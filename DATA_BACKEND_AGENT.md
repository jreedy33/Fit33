## Invariants (DB-specific — will cause data bugs / IDOR / crashes if violated)

### Type safety
1. **UUID type safety.** NEVER use `?? ""` as a fallback for `currentUser?.id.uuidString` in Supabase queries. Always `guard let userId = currentUser?.id else { return }`. Passing empty string to a UUID column causes Postgres `operator does not exist: uuid = text`.
2. **DTO null safety.** Every nullable DB column → Swift `Optional` in the DTO. Safe accessors with defaults (`opponentDisplayName: String { opponent_name ?? "Unknown User" }`).

### Pagination + duplicate fetches
3. **All Supabase fetch queries MUST include `.limit()`.** `fetchWorkoutHistory()` caps at 200; `fetchMealLogs()` caps at 100. Unbounded fetches cause memory spikes proportional to user history.
4. **No duplicate foreground fetches.** Centralized in `Fit33App.swift` scenePhase handler. `DashboardView` only handles dashboard-specific work (meals, hydration, quests). Never duplicate social/challenge/health fetches between App and Dashboard.
4a. **Wearable `force` flag MUST propagate through `HealthDataService.syncAllHealthData(force:)` to per-source methods** (`syncWhoopData(force:)`, `syncOuraData(force:)`, `syncFitbitData(force:)`). Each wearable service has its own 5-min `syncThrottleInterval`, so a top-level force that stops at HDS silently no-ops downstream — pull-to-refresh and scenePhase force syncs appear to do nothing. Fixed 2026-04-22.
4b. **Wearable widget staleness on tab return** is handled in `MainTabView.onChange(of: selectedTab)`: when returning to Dashboard (tab 0), if `WhoopService.shared.lastSyncDate` / `OuraService.shared.lastSyncDate` is >60s old, trigger a fire-and-forget force sync. Service-level `isSyncing` guard coalesces with any in-flight foreground sync. Never move this into `DashboardView.onAppear` — violates invariant #4.
4c. **WHOOP + Oura MUST be refreshed in `BackgroundChallengeSyncService.performSyncBody()`.** Both are OAuth pulls (not HealthKit writers), so without a BGTask refresh they go stale whenever the app is closed for any length of time — the Dashboard widget would show yesterday's recovery/strain/sleep on next open until the foreground Task finished syncing. Step 3b calls `WhoopService.shared.syncAllData(force: true)` (if connected), Step 3c calls `OuraService.shared.syncAllData(force: true)`. Step 3d then calls `ReadinessService.shared.recompute(force: true)` so today's blended readiness row also lands in `daily_readiness_history` from background (invariant #33 guarantees `recompute` does not recurse into wearable syncs). The scenePhase `.active` branch in `Fit33App.swift` also force-syncs both wearables in parallel with the main coordinated Task so the widget reflects live data the instant the user opens the app — the in-app service's own `isSyncing` guard coalesces the two paths when iOS just woke us.
4c-cache. **Wearable hero state on the dashboard MUST be `UserDefaults`-backed end-to-end — every `@Published` the widget reads.** `WhoopService` caches `todayRecovery` (`whoop_today_recovery`), `todayStrain` (`whoop_today_strain`), and `lastSleep` (`whoop_last_sleep`); `OuraService` caches `todayReadiness` / `todayActivity`. Every cached property MUST be (a) written in its `fetch*` method, (b) hydrated in `loadCachedDataIfNeeded()`, (c) cleared in `disconnect()`. Forgetting any one of those three steps for any one property produces a half-empty WHOOP/Oura card on cold start: the cached props render instantly, the un-cached prop sits at `--` until the next API call resolves — and if WHOOP hasn't yet scored last night's sleep at app open (8 AM cold start, recovery/strain already SCORED but sleep `PENDING`) the user sees `SLEEP --`, `ASLEEP --`, `EFFICIENCY --`, `RESP --` even though they're connected. Canonical fix: 2026-04-27 added `whoop_last_sleep` after the user reported the partial-card symptom; previously only recovery + strain were persisted. When you add a new `@Published` property the dashboard widget reads, follow all three hooks in the same PR. Also: any `result.records.first(where:)` selection from a paginated WHOOP/Oura response MUST sort by start descending first — public docs say newest-first, but a single ordering quirk would otherwise stick the dashboard on a 7-day-old record.
4d. **OAuth refresh-token rotation MUST be conditional on the server actually sending a new token.** Applies to `WhoopService.refreshAccessToken()` + `OuraService.refreshAccessToken()` (WHOOP and Oura both decode `refresh_token` as `String?`). Correct pattern: `if let rotated = tokenResponse.refreshToken, !rotated.isEmpty { refreshToken = rotated }`. The `refreshToken` keychain-setter deletes the stored entry when given `nil`, so an unconditional `refreshToken = tokenResponse.refreshToken` WIPES the refresh token any time the provider declines to rotate (WHOOP/Oura rotate on their own schedule, not on every refresh). The symptom is a zombie "connected" state — `isConnected == true` but every API call silently fails because `ensureValidToken` can't refresh an expired access token without a stored refresh token, and the `isConnectionError` catch branches in `fetchRecovery` / `fetchCycles` / `fetchSleep` / `fetchWorkouts` swallow the error to debug-log level. User-visible fix was manual disconnect + reconnect.
4c-supabase-integration-additive. **Bulk integration-status sync MUST be additive for OAuth services — never push `false`.** `SupabaseManager.syncAllIntegrationStatuses()` runs on every app launch; the OAuth columns it writes (`is_whoop_connected`, `is_oura_connected`, `is_strava_connected`, `is_fitbit_connected`) MUST only be set to `true` from this path (`local ? true : nil` pattern; nil → omitted from PATCH). The ONLY canonical `false` writers for OAuth integrations are the explicit user-action paths inside each service's `disconnect()` (the per-service `updateIntegrationStatus(integration:isConnected:false)` call). Rationale: iOS keychain entries for OAuth tokens are not guaranteed to survive app uninstall/reinstall (post-iOS-10.3 behavior is variable per-service per-device — observed in production logs as same-launch divergence: Strava token survived a reinstall while WHOOP + Oura tokens were wiped on the same launch). Pushing the empty-local state to Supabase destroyed the cloud signal "user has WHOOP/Oura linked at least once," which corrupted Bug Intel + analytics rollups, prevented any "tokens cleared on reinstall — tap to reconnect" UI prompt because cloud agreed with empty local before the UI rendered, and misrouted silent-push / edge-function targeting that gates on `is_<service>_connected`. Empty local state is not proof of user intent to disconnect. Apple Health (`is_apple_health_connected`) + InBody (`is_inbody_connected`) DO push their actual local state from the bulk path — Apple Health is HealthKit runtime auth (legitimately can revoke per-launch via Settings), InBody is BLE pairing (similar). Canonical fix: 2026-04-27 in `SupabaseManager.syncAllIntegrationStatuses()`.
4d-singleflight. **`refreshAccessToken()` MUST be single-flight — never let concurrent callers each fire their own POST `/oauth/token`.** Applies to ALL four OAuth services: `WhoopService`, `OuraService`, `StravaService`, `FitbitService` (all four shipped 2026-04-28). Canonical pattern in each file: a `private var refreshTask: Task<Void, Error>?` + a wrapper that returns the in-flight task's `.value` if one exists, otherwise spawns a new Task whose `defer` clears `refreshTask`. The actual network refresh body lives in `_performTokenRefresh()`; `refreshAccessToken()` is now ONLY the single-flight gate. Any future OAuth service (Garmin, Polar, etc.) MUST follow the same pattern. Rationale: `syncAllData(force: true)` is invoked from THREE foreground call sites in parallel on every cold start (`Fit33App.scenePhase .active` ✕ `MainTabView.onChange(of: selectedTab)` returning to Dashboard ✕ `BackgroundChallengeSyncService.performSyncBody`), and `force: true` BYPASSES the `isSyncing` guard. Inside one `syncAllData`, a `withTaskGroup` fans out 5 fetches that each call `apiRequest` → `ensureValidToken` → `refreshAccessToken` if the access token is within its 5-minute pre-expiry window. With no coalescing, ≥10 concurrent POSTs to WHOOP / Oura `/oauth/token` race with the SAME `refresh_token`. Both providers single-use refresh tokens: the first POST rotates RT_1 → RT_2, every subsequent POST gets HTTP 400 `invalid_grant`, the 400 branch in `_performTokenRefresh` calls `disconnect()` (correctly, for a real revoke — but every replay-race victim ALSO trips it), tokens are wiped, `is_whoop_connected = false` is PATCH'd to `user_profiles`, and the user has to manually reconnect on every app launch. Canonical incident: 2026-04-28 — Joe reported "I have to resync WHOOP almost every login," DB confirmed `is_whoop_connected: false` + `is_oura_connected: false` for his profile despite valid grants. Single-flight collapses N concurrent refreshes into ONE POST; awaiters share the same outcome. Zero extra network traffic, zero replay rejections, zero false disconnects. NEVER call `_performTokenRefresh` directly from `apiRequest` / `ensureValidToken` / a 401 retry — always go through the `refreshAccessToken()` single-flight wrapper. NEVER make the `refreshTask` clear path async (`Task { @MainActor in ... }` wrapper inside `defer`) — the enclosing `Task<Void, Error>` already inherits @MainActor isolation; a nested Task can race the next caller's nil-check. NEVER convert this to a semaphore / lock — Swift Concurrency Task-based coalescing is the canonical pattern (matches `RequestCoalescer` and the sync-triage Layer A.2 fan-out).
4e-hk-recursion. **`HealthKitService.syncAllData(force:)` chains into `ChallengeService.syncHealthKitDataToChallenges()` which forbids re-entry into `syncAllData(force: true)` — use `HealthKitService.refreshTodayStats()` for the today-counter refresh instead.** `syncAllData(force:)` is wrapped in `RequestCoalescer.coalesceVoid(key: "HealthKit.syncAllData.force=\(force)")`, and inside its body (`_syncAllDataBody`, `Fit33/HealthKitService.swift`) the post-sync chain calls `await ChallengeService.shared.syncHealthKitDataToChallenges()`. `syncHealthKitDataToChallenges` previously called `await HealthKitService.shared.syncAllData(force: true)` to force a today-counters refresh before pushing to per-challenge progress rows — but the coalescer joins this re-entrant call to the still-in-flight outer Task and the chain DEADLOCKS forever (outer awaits inner; inner awaits outer's `.value`). Swift Task system does NOT detect this. Canonical incident 2026-04-28 — `ChallengeService.backfillTodayProgressForChallenge` (newly introduced for accept-time bilateral progress logging) was an external caller of `syncAllData(force: true)`, the chain hung at the first `await`, and Paul's progress only landed multi-seconds later when Joe navigated away from the challenge detail and the parent Task was cancelled. Fix: `HealthKitService.refreshTodayStats()` is the canonical entry point for "I just need today's HK counters refreshed" — it calls only `syncTodayStats(authorized:)`, no TaskGroup, no chained challenge sync, no coalescer. ALL `ChallengeService` paths (`syncHealthKitDataToChallenges`, `backfillTodayProgressForChallenge`, future paths) MUST use `refreshTodayStats()`. NEVER add another `await ChallengeService.shared.syncHealthKitDataToChallenges()` reachable from `_syncAllDataBody`'s post-sync chain — same recursion shape will deadlock. NEVER call `syncAllData(force: true)` from inside `ChallengeService` or any service whose method `_syncAllDataBody` chains into.
4d-audit. **OAuth lifecycle events MUST flow through `OAuthAuditLog` so post-mortems are answerable from the next session log.** Applies to `WhoopService` + `OuraService` (extend to `StravaService` / `FitbitService` if a recurring-disconnect report ever lands on them). Required call points: (a) `init()` keychain probe — `OSStatus` per token slot via `KeychainHelper.loadWithStatus`, surfaces `notFound(-25300)` vs `locked(-25308)` vs `ok(0)` vs `missingEntitlement` so a disappeared-token report immediately distinguishes real wipe from transient lock from provisioning glitch; (b) `refreshConnectionState()` foreground state-transition with the keychain status that drove the flip; (c) `_performTokenRefresh()` enter / success / failure with HTTP status + body prefix; (d) `disconnect(reason:)` with EVERY caller passing a structured `reason` string (`user_tap`, `refresh_http_400`, `rt_wiped_keychain_readable`, `keychain_locked_no_rt`) AND a captured 8-frame stack via `Thread.callStackSymbols`; (e) `exchangeCodeForTokens` connect success with expiry + RT-presence. Persisted in `UserDefaults` (NOT App Group, NOT Keychain) under `oauth_audit_log.<service>` keys, ring-buffered to 50 entries per service. `Fit33App` dumps the trail at the top of every cold start (after `checkAuthOnly`) under `[OAUTH_AUDIT]`, so the FIRST session log after a disconnect contains the breadcrumb that explains why. NEVER call any service's `disconnect()` without a `reason`. NEVER add a new disconnect path that doesn't route through `disconnect(reason:)`. NEVER prune an `OAuthAuditLog.record` site without first confirming a replacement signal exists at the same call point — the trail is what makes recurring "WHOOP just disconnected again" reports diagnosable instead of "we'll wait for it to happen again with logs". Canonical fix: 2026-04-28 — Joe reported repeated WHOOP disconnects after the single-flight + auto-recover fixes (4d-singleflight + 4d-recover) had already shipped, and the existing `[WHOOP] Disconnected` log told us symptom but not cause; this invariant adds the missing causal breadcrumb.

4d-recover. **Wiped refresh tokens MUST auto-recover, not zombie-stay-connected.** Once `refreshAccessToken()` is invoked it MUST disambiguate "keychain transiently locked" (BGTask wake on a locked device — both `accessToken` and `refreshToken` keychain reads return `nil`, retry next foreground) from "refresh token genuinely wiped" (`accessToken` reads succeed but `refreshToken` is `nil` — permanent). Canonical probe: `let keychainReadable = KeychainHelper.load(key: "<service>_access_token") != nil` inside the `guard let currentRefreshToken = refreshToken else { ... }` branch — if `keychainReadable == true` and `refreshToken == nil`, call `disconnect()` and set `errorMessage` to a reconnect-prompting copy so Settings + the dashboard widget switch back to the "Sync <service>" reconnect CTA. Without this auto-recover, the zombie state from invariant 4d is permanent — the user sees a connected status, "Sync now" returns no data, every endpoint debug-logs `"skipped: not connected"`, and the only way out is a manual Disconnect tap they have no signal pointing toward. Logs confirming this state: 4-5 consecutive `[<SERVICE>] refreshAccessToken: no stored refresh token (keychain locked?)` warnings followed by `Recovery / Cycles / Sleep / Workouts skipped: Not connected to <SERVICE>` debugs in the same sync pass while `[INTEGRATIONS] ... <SERVICE>: true` reports the integration as connected. Canonical fix: 2026-04-27 in `WhoopService.refreshAccessToken()` + `OuraService.refreshAccessToken()`. NEVER bypass this by `disconnect()`-ing on every nil read — that re-introduces the original "spontaneously disconnected after every TestFlight update" bug 4d's defensive throw was protecting against. The accessToken-readable probe is what makes both safe. When refresh fails (HTTP non-200 OR missing stored refresh token) the service MUST call `disconnect()` before throwing so the UI surfaces the reconnect prompt instead of silently showing stale data. Strava/Fitbit decode `refresh_token` as non-optional `String`, so a missing field raises a decode error and can't silently wipe — if you ever relax those to optional, carry this pattern over. Canonical fix: 2026-04-24 in both services. Mirrors the `exchangeCodeForTokens` `if let rt = … { refreshToken = rt }` pattern that was already correct on the initial-authorization path.

### Security (RPCs + views + edge functions)
5. **RLS on every user-data table** — `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + CRUD policies scoped to `user_id = auth.uid()`. (Also in `codingrules.mdc`.)
6. **Views use `security_invoker = on`.** Never `SECURITY DEFINER` on views in `public`. (Also in `codingrules.mdc`.)
7. **RPC IDOR prevention (MANDATORY).** Every `SECURITY DEFINER` RPC taking a user-id-like parameter (`p_user_id`, `user_id_to_delete`, …) MUST either:
   1. Drop the parameter entirely and use `auth.uid()` (preferred), OR
   2. Guard at the top:
      ```sql
      IF auth.uid() IS NOT NULL AND p_user_id <> auth.uid() THEN
          RAISE EXCEPTION 'Forbidden' USING ERRCODE = '42501';
      END IF;
      ```
   `auth.uid() IS NOT NULL` lets service-role / pg_cron callers through. Canonical: `supabase/20260417_secure_get_friend_ids.sql`.
8. **Edge function CORS.** Import `buildCorsHeaders(req)` from `supabase/functions/_shared/cors.ts`. Never ship `Access-Control-Allow-Origin: *`.
9. **Every new edge function goes into the Edge Function Auth Registry in `INFRA_SECURITY_AGENT.md` in the same PR.**
10. **Edge function input validation at entry point.** Zod or manual. Standard error response: `{ error: string, code: string }`. Never log full phone numbers, auth tokens, or PII.
10d. **`fdc_id` is `BIGINT` everywhere (DB) and `Int64` everywhere (Swift / DTO / Core Data).** OFF synthetic ids are NEGATIVE bigints (`-1 × parseInt(barcode)` — up to ~13 digits → exceeds INT4 in absolute value AND we want negatives reserved for OFF as a discriminator). Every cast to `Int32` truncates them to 0 and silently strips OFF provenance round-trip. Audit 2026-04-30 caught THREE such truncations: (a) `MealEntry.fdcId` was `Integer 32` in Core Data (lightweight-migrated to `Integer 64`), (b) `SupabaseManager.saveMealToCloud` had `meal.fdcId > 0 ? Int(meal.fdcId) : nil` which wrote NULL for every OFF row (changed to `!= 0`), (c) `SupabaseManager.syncMealLogsToCoreData` cast `Int32(mealDTO.fdcId ?? 0)` (changed to `Int64`). The `meal_logs.fdc_id` column was widened to BIGINT in migration `supabase/20260802_meal_logs_off_columns.sql`. Same migration added `fiber DOUBLE PRECISION`, `sugar DOUBLE PRECISION`, `sodium DOUBLE PRECISION`, `source TEXT CHECK (usda|off|ocr|spoonacular|manual)`, `barcode TEXT`. Future rule: ANY food provenance field on a meal/log/history table starts at BIGINT, not INT4 — there is no upgrade path from "I lost the data" to "I have the data."
10e. **Cross-device meal-log cloud sync DOWN must fan-out to `DailyQuestService.onMealLogged(...)`.** `MealService.addMealEntry` (the local write path) fires per-meal-type quests + `log3Meals` + protein progress, but `SupabaseManager.syncMealLogsToCoreData` (the read path that pulls a Watch- or web-logged meal back into Core Data on iPhone) used to only `INSERT` the row and skip every quest hook. A 2026-04-30 patch adds a `newlyInsertedMealTypes: [String]` accumulator inside the `bgContext.perform`, then after `bgContext.save()` succeeds: `MealService.shared.loadTodaysMeals()` + `for mealType in newlyInsertedMealTypes { await DailyQuestService.shared.onMealLogged(mealType: mealType) }`. Protein progress is NOT bumped here (would double-count if the user is also logging locally in the same window — the next local `addMealEntry` recomputes from `todaysMeals.reduce` and corrects). Every NEW cloud-sync-down path for a metric-bearing entity (meals today; sleep / cardio / supplements tomorrow) MUST follow this pattern: accumulate inserts during the bg-perform, then dispatch quest hooks after the save commits.
10f. **Detailed nutrition (`fiber`, `sugar`, `sodium`) and provenance (`source`, `barcode`) are now persisted on `MealEntry` (Core Data) + `meal_logs` (DB) + `MealLogDTO` (Swift) + `FoodEntry` (struct).** Pre-2026-04-30, fiber/sugar/sodium were computed by `FoodDetailsView.currentNutrition` and shown to the user, then THROWN AWAY at `MealService.addMealEntry` time and recomputed (often as 0) on every render — Dashboard fiber goal / sodium-limit quests were impossible. Same for `source` / `barcode` (lost ODbL attribution on render of saved OFF meals; lost barcode-cache hits across devices). Adding a new column to this set requires a 5-spot edit: (1) `Fit33/DataModel.xcdatamodeld/.../contents` (lightweight migration — optional attribute), (2) `Fit33/NutritionModels.swift::FoodEntry`, (3) `Fit33/MealService.swift::MealEntryData` + `MealEntry.toMealEntryData()` mapper (the SINGLE canonical mapper used by all three load paths — never re-add inline initializers), (4) `Fit33/SupabaseDTOs.swift::MealLogDTO`, (5) DB migration adding the column to `meal_logs`. The mapper is the choke point: future cross-cutting nutrition fields (e.g. caffeine, added sugar) only touch the mapper once, not three times.
10c. **Food search has TWO data sources behind ONE edge function: USDA FoodData Central (whole foods, lab-verified) AND Open Food Facts (packaged products, barcodes).** Helper lives in `supabase/functions/_shared/openFoodFacts.ts`. The edge function `usda-food-search/index.ts` fans out 4-way in parallel inside `handleSearch` (Foundation + SR Legacy + Branded + OFF) and exposes a separate `case "barcode":` action for the camera-scan flow (`Fit33/BarcodeScannerView.swift` → `FoodDatabaseService.searchByBarcode`). Cached in the SAME `food_items` table via `food_items.barcode` (PARTIAL UNIQUE INDEX where `source = 'off'`) + `food_items.source IN ('usda','off')` (CHECK). OFF rows use a SYNTHETIC NEGATIVE `fdc_id` derived from the numeric barcode (`syntheticFdcIdForBarcode` in the helper; `fdc_id` widened to BIGINT in migration #165) so the existing `onConflict: "fdc_id"` upsert path stays unchanged — by construction collision-free with USDA's positive int32 fdcIds. **Ranker tiers** (must match server ↔ iOS — `calculateFoodScore()` in the edge function and `calculateRelevanceScore()` in `USDAFoodService.swift`): `Foundation` (-50000 server / -200000 iOS) > `SR Legacy` (-40000 / -150000) > `Survey (FNDDS)` (-10000) > **OFF (+5000 server / -50000 iOS)** > `Branded` (+30000 / 0). OFF beats USDA Branded because OFF has `unique_scans_n` popularity + `nutriment_data_completeness` quality signals that USDA's Branded grab-bag lacks. **Unit conversion is non-obvious**: OFF stores micronutrients in **grams** (sodium, cholesterol, calcium, iron, vitamin C — all `_100g`); USDA standard is **milligrams**. The shape translator (`transformOFFToUSDAShape` in the helper) MUST × 1000 — sodium especially. Skipping the conversion makes Doritos report "0.6 mg sodium" instead of 600 mg and silently breaks daily-sodium quests. Test with a high-sodium product after any change here. **License: ODbL** — every UI surface that renders an OFF row MUST attribute "Data: Open Food Facts" (FoodDetailsView footer when `source = 'off'`). NEVER strip the source field from an OFF row.

10b. **iOS callers of `requireUserAuth`-protected edge functions MUST send the user's session JWT in `Authorization: Bearer <accessToken>`, NEVER `AppConfig.Supabase.anonKey`.** The anon key goes on the SEPARATE `apikey:` header (the Supabase API gateway needs that one to route the call). Any edge function that imports `requireUserAuth` from `_shared/cors.ts` calls `supabase.auth.getUser(token)` on the bearer token; the anon key is not a user JWT and gets rejected with HTTP 401 — but the gateway still routed the call, so the symptom is "endpoint reachable but every call 401s in <500ms," not a connection error. Canonical pattern (mirrored from `Fit33/ContentModerationService.swift::checkContent`): `let session = try await SupabaseManager.shared.client.auth.session` → bail if it throws (no user, fall back to local), then `request.setValue("Bearer \(session.accessToken)", forHTTPHeaderField: "Authorization")` + `request.setValue(AppConfig.Supabase.anonKey, forHTTPHeaderField: "apikey")`. Applies to EVERY hand-rolled `URLSession` call into `\(AppConfig.Supabase.url)/functions/v1/...` whose function uses `requireUserAuth`. The Supabase-Swift SDK's `client.functions.invoke(...)` attaches the JWT automatically — the bug class only exists on the URLSession path. Canonical incident: 2026-04-30 — `Fit33/FoodDatabaseService.swift::searchFoods` shipped the anon key on `Authorization`, every food search 401'd at the edge, the iOS side classified it as transient and silently fell back to the 380-item local list (4 fingerprints in one user's session: `022843d7…`, `b99dfd29…`, `f871f70a…`, `8e070db8…`); user-visible symptom was "search for 'potato chips' or 'caesar salad' returns nothing" because the local list didn't have them and the cloud was permanently locked out. Closed by routing through `client.auth.session.accessToken` + adding the items to the local fallback. NEVER copy/paste a URLSession edge-function call without auditing its `Authorization` header first; if you find one using `anonKey`, treat it as a P0 break.

### Contracts with Swift
11. **Return-type contract with Swift.** SQL `RETURNS jsonb` → Swift decodes a `Decodable struct`, never `Bool`. SQL `RETURNS boolean` → `Bool`. If you change a RETURNS clause, grep the RPC name in `Fit33/SupabaseManager.swift` and all `*Service.swift` and update decoders in the same commit.
12. **SQL `RETURNS TABLE` functions:** set `#variable_conflict use_column` at the top if any parameter name collides with a column name (hard-won 2026-03-29).
13. **SQL RECORD types** — never use anonymous `ROW(0,0,0)` to init a `RECORD`; the fields have no names. Use `SELECT 0 AS field_name, ... INTO v_record` instead.

### Social + moderation
14. **Moderation flip propagates via realtime.** The moderation webhook sets `is_hidden = true` after insert. Any client UI that persists the sender's own row (chat, activity feed) MUST subscribe to `UpdateAction` on that table and drop rows where `is_hidden` flipped true. Canonical: `RealtimeService.subscribeFriendActivityFeed` + `PrivateChallengeService` UPDATE sub. Server RPCs filter hidden rows, but local caches don't refresh without this.
15. **Legacy `group_challenge_members` is revoke-hardened.** RLS enabled; `INSERT/UPDATE/DELETE` revoked from `authenticated`, `ALL` revoked from `anon`. Only `service_role` + SECURITY DEFINER RPCs may write. Use `challenge_participants` for the live challenge system. See `supabase/20260418_group_challenge_members_invariant.sql`.
16. **Social compliance RPCs.** `get_blocked_users()` and `report_content(p_table_name, p_record_id, p_reported_user_id, p_content_snippet, p_reason)` are the canonical App Review compliance surfaces. `report_content` hard-filters `p_table_name` against an allowlist: `private_challenge_chat`, `challenge_reactions`, `shared_workouts`, `group_challenges`, `private_challenges`, `community_challenges`, `friend_activity_feed`, `user_profiles`. Writes to `content_moderation_log` with `flagged_categories=["user_report"]`.

### Realtime

### Exercise performance history — single canonical writer (2026-04-27 — hard-won)
17b. **`ExerciseHistoryService.saveExercisePerformance()` is the SINGLE canonical writer for `exercise_performance_history`.** Invoked from `ActiveWorkoutView+Persistence.saveExercisePerformanceHistoryWithData()` (called by the active-workout completion path with captured sets data, race-safe vs. `WorkoutManager.exerciseSetsData` clear). Populates `total_reps`, `max_weight`, `max_reps`, `avg_weight`, `avg_reps`, `total_volume`, `total_sets`, `workout_duration_seconds`, `had_failure_set`, `had_dropset`, **`exercise_id`** (canonical Core Data UUID, added 2026-04-29 / migration #164 — see invariant 17e), plus per-set rows in `exercise_set_history` (also carrying `exercise_id`), plus `updatePersonalRecords` → `exercise_personal_records` upsert. ### Exercise-history reads MUST be id-strict (2026-04-29 — cross-pollination class)
17e. **The active-workout "Previous Max" tile row reads `exercise_performance_history` by EXACT `exercise_id`, never by `exercise_name`.** Migration #164 (`supabase/20260802_exercise_performance_id_match.sql`) adds nullable `exercise_id UUID REFERENCES exercises(id) ON DELETE SET NULL` to BOTH `exercise_performance_history` and `exercise_set_history` + a partial index `(user_id, exercise_id, workout_date DESC) WHERE exercise_id IS NOT NULL`. The legacy by-name path is preserved on the service for non-tile use cases but MUST NOT be wired into `ExerciseCard.loadRecentSessionsIfNeeded()`. **Why**: when the catalog has two distinct `Exercise` rows that share `.name` (custom + catalog row, equipment-variant merges from CMS sync, sibling rename collisions), the by-name path renders one user's history on a different exercise's card — user-visible bug filed 2026-04-29 ("some exercises are showing max performance on things i haven't done"). The migration backfills `exercise_id` for `(user_id, exercise_name)` tuples that resolve unambiguously in the `exercises` catalog (`HAVING COUNT(*) = 1`); ambiguous names — the bug class itself — intentionally remain NULL so the tile row hides until the user logs a fresh session against the specific id. **Save side**: `saveExercisePerformance(exerciseId:exerciseName:...)` always passes `exercise.id` from `ActiveWorkoutView+Persistence.swift`. ### RPC ↔ schema column read invariant (2026-04-27 — latent-bug class)
17c. **Every column referenced inside a `SECURITY DEFINER` RPC body MUST exist on the target table from the SAME migration that introduces the read.** Conditional-branch reads (`IF v_x THEN SELECT col INTO v ... FROM tbl ...`) are especially dangerous: the column-missing error stays hidden as long as the gate stays `FALSE`. Canonical incident: `user_daily_quests.bonus_claimed` was referenced by every `get_daily_quests` overload from `20260324_adaptive_quest_selection.sql` forward (current head: v4 in `20260703_get_daily_quests_brief_signals.sql`) but the original `daily_quests_migration.sql` `CREATE TABLE user_daily_quests` shipped without the column. The bug stayed dormant for 8 months because the SELECT was gated on `IF v_all_complete THEN` — CI fixtures never completed all 3 daily quests. The instant a real user finished their last quest of the day, every subsequent dashboard refresh raised PostgreSQL 42703 (`column "bonus_claimed" does not exist`) and the slate collapsed to `defaultGoals()` until midnight (bug-intel fingerprints `76860b32`, `8e0764bf`, `4729e709`, `537be0ee` — 22 occurrences, build 1.38(59), all on 2026-04-27). Closed by `supabase/20260707_user_daily_quests_bonus_claimed.sql`. **Authoring rule**: when you `git grep` an RPC's `SELECT <col>` patterns, EVERY column on the LHS or RHS must trace to a `CREATE TABLE` or `ADD COLUMN IF NOT EXISTS` in a migration that runs at-or-before the RPC body migration — not "should exist eventually," from the same PR. The pre-commit migration check should fail any new RPC that references a column not present in `information_schema.columns` snapshot.

### Edge function error wrapping in `supabase-functions-swift` (2026-04-27)
17d. **`FunctionsError.httpError(code:data:)` collapses non-2xx responses to `"Edge Function returned a non-2xx status code: <code>"` — the response body is unreachable from `.localizedDescription`.** Any `NetworkErrorClassifier` body-string pattern (e.g. `"forbidden: new_user_id must match caller"`) MUST therefore also be matched at the call site BEFORE classification, OR the classifier-bypass `.error` log will create a bug-intel fingerprint per occurrence. The classifier already had the body-string pattern but never saw the body, so every onboarding flow created fingerprints `b242269c`, `65f3c668`, `1951d472`. Pattern (verified canonical): catch the bare `"non-2xx status code: 403"` at the call site, log at `.debug`, fall through to the classifier ONLY for unexpected status codes. Applies to any iOS-side `.functions.invoke()` whose edge function uses an IDOR guard — `notify-contacts-user-joined`, future `claim_*` RPCs, etc.

### Supabase Swift client — UUID handling
24. **Pass Swift `UUID` directly to `uuid` columns — NEVER `uuidString` / `String`.** Applies to `.insert()`/`.upsert()` struct fields AND `.eq()` filter values. The Supabase Swift client's `Encodable` conformance serializes `UUID` correctly; passing a `String` causes a type mismatch at the PostgREST boundary. ### DTO null-safety (reinforces #2)
25. **Integer columns without `NOT NULL DEFAULT` → `decodeIfPresent` + safe default in Swift.** Never assume a DB integer is non-null. Pattern:
    ```swift
    self.reps = try container.decodeIfPresent(Int.self, forKey: .reps) ?? 0
    ```
    Missing a default produces silent decoder failures that drop the entire row.

### Opponent-progress silent-push fan-out (2026-04-26 — Phase 7b)
50. **`challenge_daily_progress` + `private_challenge_daily_progress` AFTER INSERT/UPDATE OF `progress_value` triggers MUST share the recursion / monotonicity / same-day guard convention.** Canonical: `supabase/20260625_opponent_progress_silent_push.sql::notify_opponents_on_progress_change()`. Guards (in order): (a) `pg_trigger_depth() > 1` skips fanout-mirrored writes (#48 above) — without this we'd 3× the silent-push fan-out per real movement; (b) STRICT-INCREASE check `NEW.progress_value > OLD.progress_value` (or positive INSERT) — `GREATEST()` no-op writes still produce UPDATE rows with identical values; pushing on those would be pure noise; (c) same-day floor `progress_date >= today_utc - 1` — backfills of older days never wake opponents. When you add a new daily-progress table that should fan-out, attach this same trigger function — it auto-detects via `TG_TABLE_NAME`. Edge function side: extend `THROTTLE_WINDOWS_MS_BY_SOURCE` in `supabase/functions/wake-challenge-opponents/index.ts` for the new source, keep per-source `triggered_by` filter on the `silent_push_wake_log` lookup so each lane throttles independently. 50a. **Widget Freshness Sprint 7e throttle ladder (2026-04-27).** End-to-end opponent-progress latency is gated by FOUR throttles that must stay tuned together so no single layer becomes the bottleneck: (1) writer main-app `Fit33/BackgroundChallengeSyncService.throttleStepsInterval = 60s` (was 120s) — HK observer steps push throttle on the LITE wake path; (2) writer widget extension `RunningActivityWidget/ActiveChallengeWidget.widgetPushThrottle = 30s` (was 120s) — only fires when iOS schedules a widget timeline tick (~20 min cadence) AND the per-value dedupe (`widgetPushValueKeyPrefix`) passes, so 30s is effectively a "never throttle a real tick" floor for the suspended-app case; (3) edge function `THROTTLE_WINDOWS_MS_BY_SOURCE.progress_update = 20_000` (was 60_000) — per-recipient cap, defense-in-depth against runaway writers since Apple's APNs silent-push budget is the real ceiling; (4) reader `Fit33/ActiveChallengeWidgetBridge.minReloadInterval = 4.0s` (was 8.0s) — `WidgetCenter.reloadAllTimelines()` coalesce window. NEVER raise any of these without raising the matching layer or the chain becomes asymmetric. Server-side `GREATEST()` on `log_challenge_progress` and the per-value dedupe in (2) make over-pushing safe — the only cost of dialing further down would be marginal CPU on the LITE sync path. Roll back path: revert all four call sites in lockstep — partial revert recreates the asymmetry.

### Challenge daily reset — caller timezone + dawn-ghost guard (2026-04-24)

Canonical branch (mirrored across all three RPCs):
```
WHEN p_allow_decrease
     AND EXCLUDED.progress_value = 0
     AND <table>.progress_value > 0
    THEN <table>.progress_value
WHEN p_allow_decrease THEN EXCLUDED.progress_value
```
in the upsert `DO UPDATE SET progress_value = CASE …` clause; companion branch in the `target_hit` CASE preserves the existing target_hit so a hit-row doesn't flip to a miss-row when the 0 push is rejected.
