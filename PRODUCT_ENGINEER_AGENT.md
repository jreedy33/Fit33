## Invariants (PE-specific — will cause bugs if violated)

### Auth + data loading
1. **Auth guard on every social fetch.** Every async fetch in social/challenge/friend services starts with `guard SupabaseManager.shared.isAuthenticated else { return }`. `MainTabView` appears on `hasCompletedOnboarding`, NOT `isAuthenticated` — `.task` fires before auth completes.
2. **Network calls in parallel.** All independent network calls in `.task`/`.onAppear` use `async let` groups, never sequential `await`. Dashboard runs all 14 fetches in one group.
3. **`@FetchRequest` MUST set `fetchLimit`** when displaying a bounded list (e.g. `prefix(10)` → `fetchLimit: 10`). Dashboard uses 10.
4. **No duplicate fetches across `.task` and `.onAppear`.** `.onAppear` fires on every tab return. Foreground refresh is centralized in `Fit33App.swift` scenePhase.

### Navigation
5. **Same destination = same presentation.** Multi-step creation = `.fullScreenCover` + inner `NavigationStack`. Detail push = `NavigationLink`. Quick picker = `.sheet`.
6. **Never nest `NavigationStack` inside a pushed detail view.** Pushed settings views (`HealthKitSettingsView`, `StravaSettingsView`, etc.) must NOT wrap themselves in `NavigationStack` — only sheet/fullScreenCover entry points host one. Nesting breaks `.navigationDestination` and bounces to root on `dismiss()`.
7. **No placeholder destinations in shipped `Destination` enums.** If a real view isn't ready, remove the entry point (chevron/card). "Coming Soon" screens = App Review rejection. Canonical example: `DashboardRoute.programDetailsPlaceholder` (entry removed 2026-04-17).
8. **Every Settings row must do something.** Empty `// Navigate to X` closures are ship blockers. "Help / Rate / Support" → `SFSafariViewController` on `AppConfig.Support.helpCenterURL` or `SKStoreReviewController`.

### Widgets + dashboard
9. **Widget isolation in ScrollViews (mandatory).** Any widget in a ScrollView with 5+ siblings MUST be its own `View` struct that owns its service subscriptions (`@StateObject`/`@ObservedObject`). Parent views pass only stable values to wrappers. Canonical: `DashboardQuestsWrapper`, `DashboardHeaderWrapper`, `DashboardChallengesWrapper`, `DashboardWorkoutCarouselWrapper`, `DashboardQuestCelebrationWrapper`. Parent `DashboardView` keeps services as plain `let`, not `@StateObject`.
10. **Celebration overlays MUST live in a wrapper.** Overlays that read service `@Published` state (`showQuestCompletionCelebration`, toasts, banners) must be in a dedicated wrapper with `@StateObject`. Reading from a plain `let` in the parent body = overlay never fires.
11. **Horizontal drag in vertical ScrollView:** `.simultaneousGesture(DragGesture(minimumDistance: 25))` — never `.highPriorityGesture` with low minimum. High priority + 8pt steals vertical scroll touches. *Exception*: carousel that hosts tappable buttons uses `.highPriorityGesture(DragGesture(minimumDistance: 25))` to prevent button taps during swipes.
12. **Dashboard notification cards = one carousel.** All notification types (friend requests, received workouts, 1v1/group/private invites) live in `DashboardNotificationCarousel` (in `DashboardModels.swift`). Add new types to the `NotificationItem` enum, never a sibling container. Sort: friend requests first, then oldest-first.

### Social writes
13. **Every successful social write ends with a push flush.** `FriendService`, `ChallengeService`, `CommunityChallengeService`, `PrivateChallengeService`, `ActivityFeedService`, `CardioActiveWorkoutView.saveWorkout` all call `PushNotificationService.shared.flushPushNotificationQueue(triggeredBy:)` after the write succeeds.
14. **Every workout-type completion calls its `UserManager.complete*Workout(...)`.** Strength via `completeWorkout`, cardio via `completeCardioWorkout`. Skipping breaks XP, streak, feed, quests, challenges, and badges silently.

### Active workout state integrity
14b. **Every mutation of `ActiveWorkoutView.exercises` MUST call `syncExercisesToWorkoutManager()`.** `exercises` is local `@State`; `WorkoutManager.currentExercises` is the ground truth that `saveActiveWorkoutToStorage()` serializes to UserDefaults. Any add / remove / shuffle / drag-reorder that skips the sync gets silently dropped when iOS suspends or kills the app — the user returns to only the original `startWorkout()` list. Canonical call sites: `removeExercise(at:)`, `shuffleExercise(at:with:)`, `onDragEnded` (+Layout), and the `onAddExercise` callback in the fullScreenCover (+Layout).
14d. **ExerciseCard "Previous Max" tile row reads through `ExerciseHistoryService.shared.fetchRecentSessions(forExerciseId:limit:)` — never subscribe `ExerciseHistoryService` as `@ObservedObject` from inside `ExerciseCard`.** The tile row sits above `columnHeaders` and renders a leading `"Previous Max:"` label followed by up to 2 condensed tiles (top-set weight + short date) sourced from the `exercise_performance_history` table. **Strict-id read (2026-04-29, migration #164)**: the tile row queries by `exercise.id` (canonical Core Data UUID, mirrored on `exercise_performance_history.exercise_id`) — NOT by `exercise_name`. The legacy name-keyed read (`fetchRecentSessions(for:limit:)`) is preserved on `ExerciseHistoryService` for non-tile-row use cases but MUST NOT be called from `ExerciseCard.loadRecentSessionsIfNeeded()`. The id-strict read also filters `total_sets > 0` defensively so a legacy ghost row never re-surfaces. When the user's catalog has two distinct `Exercise` rows that happen to share `.name` (custom + catalog row, equipment variants merged under one canonical name during a CMS sync), the name-keyed path used to render `"Previous Max: 185 lb"` on a card the user had never trained — id-keyed reads are the fix. If `exercise.id` is `nil` OR no id-tagged history exists yet, the tile row hides; never falls back to name. Capped at 2 (was 3 until 2026-04-27) so the row stays single-line — a 3rd tile wraps "Apr 26"-style chips onto a second line on iPhone SE / 13 mini. Three call-site numbers MUST stay in sync if you ever change the cap: `RecentSessionsTilesRow.body::prefix(2)`, `ExerciseCard.loadRecentSessionsIfNeeded::limit: 2`, `ExerciseHistoryService.fetchRecentSessions::limit: Int = 2` (default on BOTH the by-id and by-name overloads). Weight value rendered is `session.maxWeight` (heaviest single set in that workout) with `session.avgWeight` as a soft fallback for legacy rows where `max_weight = 0` but `avg_weight > 0` — never display avg-weight as the primary value, it confuses users alongside the suggested-weight column ("worked 70×8 → tile says 67"-style mismatch reported 2026-04-27). Storage rules: `ExerciseHistoryService` owns `recentSessionsByIdCache: [UUID: [ExerciseSessionSummary]]` (id-keyed, the active read path) AND a legacy `recentSessionsCache: [String: ...]` (name-keyed, fallback) + matching `inFlightSessionTasksById` / `inFlightSessionTasks` dedupe maps. Both caches (including empty arrays) are cleared by `clearCache()` and per-exercise inside `saveExercisePerformance` so a freshly-finished workout shows up in the tile row on the next open. ExerciseCard holds `@State private var recentSessions: [ExerciseSessionSummary]` + `didLoadRecentSessions: Bool` — fetched lazily once on `.onAppear`, reset + refetched on `.onChange(of: exercise.id)` (shuffle/replace path), id-stale-guard before assigning. **Do NOT** add `@ObservedObject var historyService = ExerciseHistoryService.shared` to ExerciseCard — that re-renders every card on every cache mutation and violates Widget Isolation (Invariant 9). The tile row uses `Color.cardBackgroundSecondary` + `CornerRadius.sm` + `ds_labelMedium` / `ds_labelSmall` (NOT `.sleekCard` — these are subtle list-row chips, not primary cards) and respects `useKg` for unit conversion (`* 0.453592`).
14c. **`ActiveWorkoutView.workoutBackground` MUST layer an opaque `Color` BEHIND `AnimatedOrbBackground.workoutStatic`.** ActiveWorkoutView is rendered as a `zIndex(10)` overlay on top of `WorkoutTabView` (see `WorkoutTabView.swift` Layer 3), which has its own orb background, "Workout" header, exercise list, and tab bar. `AnimatedOrbBackground.workoutStatic` uses `AdaptiveGradient.universalDark` in dark mode, which begins with `purple.opacity(0.2)` + `blue.opacity(0.1)` — translucent. Without an opaque base (`Color(red: 0.04, green: 0.04, blue: 0.06)` dark / `Color(.systemGroupedBackground)` light), the underlying tab bleeds visibly through the active workout, producing a stacked / "ghosted" UI. Active workout is the only full-screen overlay using a `zIndex` push (not a system fullScreenCover/sheet, which iOS opaques automatically) — never strip the opaque base when refactoring this background. Also use `workoutStatic` not `workout` here: every CPU cycle goes to rest timers + screen-stays-on, no decorative animation can compete.

14r. **Strava API Agreement compliance contract — three-prong delete cascade (2026-05-02, day-of submission for production access).** Strava grants production-access apps the right to call their API on behalf of arbitrary athletes IFF the app honors three "deletion within 48h" obligations. The app's compliance surface is split across three files; never let one drift without the others. (a) **Activity-delete webhook leg:** `supabase/functions/strava-webhook/index.ts` MUST handle `object_type=activity, aspect_type=delete` events by `DELETE FROM cardio_workouts WHERE user_id=X AND source='strava' AND external_id=object_id` via the function's service-role client. NEVER soft-delete (we previously did and it was a violation). (b) **Athlete deauthorization webhook leg:** the same function MUST also handle `object_type=athlete, aspect_type=update, updates: {authorized: "false"}` (Strava sends the value as a *string* — handle both `"false"` and JSON `false`) by purging EVERY `cardio_workouts` row with `source='strava'` for that user AND the user's `user_strava_tokens` row. The webhook resolves owner_id → user_id via `get_user_id_for_strava_athlete` BEFORE the type-switch. (c) **In-app Disconnect leg:** `Fit33/StravaService.disconnect(triggeredByExternalRevoke:)` MUST call the `delete_my_strava_data()` RPC (migration `supabase/20260822_strava_compliance.sql` — auth.uid()-pinned SECURITY DEFINER, no user_id arg per Infra-Security #9) which performs the same cardio_workouts + tokens cascade-delete server-side. The disconnect alert in `StravaSettingsView` MUST say "Disconnect & Delete Data" + explicit data-deletion message — DO NOT revert to the old "Your synced activities will remain" wording (it was a hard violation). ### Quests — live value source
25. **Every `liveCurrentValue` switch case MUST use `max(localValue, quest.currentValue)`** so progress never regresses below the last server sync when HealthKit/services haven't repopulated local state. Exceptions: binary quests where the local check is authoritative (e.g., `logBreakfast` reads `todaysMeals` directly).

25-binary. **Binary "Hit your X goal" quests must compute the real local threshold and snap progress 0 → targetValue at the threshold — never feed raw counter values into a `target_value=1` denominator.** The shared `quest_templates` row carries a binary completion stamp; the iOS UI is responsible for translating the user's real-world progress into the binary outcome. Canonical pattern in `DailyQuestViews.liveCurrentValue` (matches the FE invariant 18b mechanic side):
```swift
case .hitXGoal:
    let live = realLocalValue >= DailyQuestService.shared.computeUserXGoal()
        ? quest.targetValue : 0
    return max(live, quest.currentValue)
```
Returning `max(rawCounter, currentValue)` against `target_value=1` pegs the progress bar at 100% on the first observation > 0 (any step / any gram of protein), making the bar lie about completion. Canonical incident: 2026-04-27 `hit_protein_goal` rendered "Eat 1g protein today" with a 100%-pegged bar after the user's first meal even though the server hadn't completed the quest. Same rule applies to copy: `dynamicDescription` MUST read from `DailyQuestService.computeUserXGoal()` (or its sibling for that domain — `HealthKitManager.stepGoal` for `hit_step_goal`, etc.), NEVER from `quest.targetValue`. The `AdvancedIntelligenceService.liveQuestValue` + `nudgeMessage` switches MUST follow the identical pattern — copy/UI-divergence between the legacy recommendation cache and the live widget surface is a regression vector that produced the 1g protein bug. ### Push notifications

33. **Inbound APNs payloads parse through `PushPayload.swift` (Codable), never raw `userInfo[...]` access.** `Fit33/PushPayload.swift` is the single decoder for remote pushes. It parses top-level `type`, `category` (`PushNotificationCategory` enum, parity-tested against `notification_categories` table — see `Fit33Tests/PushPayloadParityTests.swift`), `intent_kind`, `intent_id`, `notification_id`, plus a `silent` derived flag (true when `aps.content-available=1` AND no `aps.alert`). Every new server-emitted payload field MUST be added to the Codable struct in the same PR — gracefully degrading on unknown keys is fine, but stringly-typed access in `NotificationManager` / `SilentPushHandler` is forbidden. Reproducing the typed-payload path eliminates the entire class of "I added `intent_kind` server-side and forgot to update the iOS switch" bugs that motivated Phase 1 of the Smart Notification Engine overhaul (Migration #169–170, 2026-08-01).

34. **Tap routing is exhaustive — every server-emitted `type` value MUST appear in BOTH `NotificationManager.knownNotificationTypes` AND `NotificationManager.handleNotificationType(_:userInfo:)`.** The allowlist test (`PushPayloadParityTests.phase3IntentKindsAreAllowlisted`) keeps the two in sync — adding a server intent kind without registering an iOS route is a silent regression where the tap opens the dashboard instead of the relevant screen. Smart Notification Engine Phase 1 fixed three holes (`challenge_declined`, `challenge_update`, `challenge_reaction`) and added 12 orchestrator-driven types (`league_started`, `rivalry_behind`, `recovery_alert`, `sleep_debt`, `hydration_pace`, `streak_risk`, `friend_workout_match`, `pr_opportunity`, `overdue_muscle_group`, `strava_celebration`, `morning_kickstart`, `meal_reminder`, `protein_deficit`, `breakfast_reminder`). Deep-link destinations are defined in `DeepLinkManager.Destination`; new types route through there, never through one-off side effects.

35. **Notification permission asks go through `PushPermissionCoordinator.shared.ensureAskedOnce(useSoftPrompt:)` — exactly ONE place.** Apple grants the system permission dialog once per install. Pre-Phase 1 we had three competing ask paths (`MainTabView.task`, `NewOnboardingView+Completion`, `PushNotificationService.registerForPushNotifications`) that raced and burned the dialog. The coordinator fans them all in: it presents `NotificationPrimerSheet` (soft prompt with category previews) on first call when status is `.notDetermined`, then triggers the system dialog on `requestSystemPermission()`. Adding a fourth ask path is a regression — route through the coordinator instead.

36. **`NotificationManager.syncPreferencesFromCloud()` runs once after auth-ready (called from `Fit33App.swift` post-auth `Task`).** Server `user_notification_preferences` (managed by Supabase RPCs `get_my_notification_preferences` / `snooze_notification_category` / `clear_notification_snooze` from migration #169) is the source of truth across devices. Conflict policy: server-newer-wins compared against `lastLocalPrefsChangeKey` UserDefaults stamp. The `didSet` writers on `NotificationManager` @Published prefs auto-stamp this via `recordLocalPrefsChange()`. Skipping the sync on second-device install means a user who turned off `recovery_alert` on iPhone keeps getting them on iPad — the exact "preferences are one-way" bug Phase 1 closed.

37. **Forward-leaning push events MUST be reported via `PushEventReporter.shared.report(_:userInfo:)`.** Foreground delivery (`willPresent`), tap (`didReceive` `.actionIdentifier == UNNotificationDefaultActionIdentifier`), action button (`didReceive` with custom action id), and explicit dismissal (`.dismissActionIdentifier`) all post to the `record-push-event` Edge Function so the CMS Health & Funnel + Failed Deliveries tabs can compute open rates. Background delivered events ship via the iOS Notification Service Extension (added in a follow-up Xcode target). Reporting is `Task.detached` so it never blocks the main thread; auth status is checked before the network call. The orchestrator's `get_engagement_score(user_id, category, hour_of_day)` RPC reads from `notification_engagement_history` which `record-push-event` writes to — skipping the report breaks the smart-timing feedback loop.

### Sync Triage 2026-04-27 (foreground social re-sync + realtime self-healing + onboarding restoration)
28-sync-a. **Foreground social re-sync is UNCONDITIONAL — never gate on `RealtimeService.shared.isConnected`.** `Fit33/Fit33App.swift` scenePhase `.active` MUST run a single `forceReconnectIfStale()` followed by a 10-fan `async let` group: `FriendService.fetchPendingRequests`, `ChallengeService.fetchPendingInvites`, `ChallengeService.fetchPendingSentChallenges`, `ChallengeService.fetchActiveGroupChallenges`, `PrivateChallengeService.fetchPendingInvites`, `PrivateChallengeService.fetchMyChallenges`, `CommunityChallengeService.fetchMyChallenges`, `ActivityFeedService.fetchFeed`, `FriendService.checkForNewWorkouts`, `ChallengeService.fetchActiveChallenges`. The previous `if !RealtimeService.shared.isConnected` retry block hid a class of "iOS silently killed our WebSocket while suspended" bugs: `isConnected` stayed `true`, the conditional bypassed every RPC fetch, and the dashboard rendered yesterday's notifications until the user dragged-to-refresh manually (canonical incident 2026-04-27 — Paul saw Joe's friend-request push but the carousel card never landed). The 10 RPCs are all coalesced via `RequestCoalescer` so duplicate calls from realtime subscribe-handlers are free. **The 1v1 active challenges fetch (`fetchActiveChallenges`) is non-negotiable here** — it drives BOTH the in-app `DashboardChallengesWrapper` widget AND the home-screen `ActiveChallengeWidget` (via `ChallengeService.cacheActiveChallenges` → `ActiveChallengeWidgetBridge.publish` → `WidgetCenter.reloadAllTimelines`). Earlier versions kept these widgets fresh ONLY indirectly — when foreground HealthData sync wrote the user's own progress, the realtime `OWN_DAILY_PROGRESS` UPDATE event fired → `RealtimeService.throttledChallengeFetch()`. That chain breaks whenever there's no fresh HK data to push (no event = no refetch = stale widget) or when an event was missed during the iOS-killed-socket window between disconnect and re-subscribe. Canonical incident 2026-04-28 — user reported "active challenge widgets in-app and on home screen don't update in real-time anymore" after the 1.38(60) sync triage shipped; the carousel-focused 9-fanout had explicitly omitted `fetchActiveChallenges` while every other widget-feeding service (group / private / community) was already explicit. NEVER add a new `if !isConnected` short-circuit here; if you find one, delete it. NEVER drop `fetchActiveChallenges` from this fan-out "for performance" — the 5s internal throttle + RequestCoalescer + 1s `fetchMinInterval` make duplicate calls free, and the widget freshness contract depends on it. Mirrors and supersedes the 2026-03-29 "Phase 3+4 retry" pattern.
28-sync-b. **`RealtimeService.forceReconnectIfStale()` is the canonical foreground reconnect entry point — `connect()`'s 10s throttle is bypassed when `lastEventReceivedAt > staleEventThreshold` (30s).** `Fit33/RealtimeService.swift` tracks `lastEventReceivedAt` on every successful `postgresChange` event delivery; `connect()`'s "skip — connected Ns ago" branch now also requires `recentEvent` (`lastEventReceivedAt < 30s ago`) before short-circuiting. `forceReconnectIfStale()` is the public API the app calls on foreground (`.active`): it disconnects + reconnects only when stale, otherwise returns immediately. Inside `connect()`'s `Task.detached` post-connect resync, the same 10-fan social group from invariant 28-sync-a runs (including `ChallengeService.fetchActiveChallenges` for the 1v1 active widget + home-screen widget), making `connect()` the canonical "everything social, refreshed" entry point — so a fresh subscribe after a stale reconnect picks up any events missed during the dead-socket window. NEVER raise `staleEventThreshold` above 60s without raising the matching foreground call interval — sync staleness is bounded by `min(scenePhase fire cadence, staleEventThreshold)` and 30s is the contract user-facing latency depends on. NEVER set `lastEventReceivedAt` from the connection-handshake path; it MUST advance only on real `postgresChange` deliveries, otherwise an idle connection self-reports as "fresh" and the staleness check loses its signal.
28-sync-c. **Onboarding checkpoint restoration MUST gate on `!userManager.hasCompletedOnboarding`, NEVER on `!supabaseManager.isAuthenticated`.** `Fit33/NewOnboardingView.swift::onAppear` calls `restoreFromCheckpoint()` for any user mid-onboarding regardless of auth state, because by step ≥7 (after `handleAuth()` creates the Supabase user — see invariant 15) the user IS authenticated but still mid-flow. The previous `!isAuthenticated` gate produced the canonical incident 2026-04-27 — user on "sync contacts" step taps "Open Settings" → grants Full Access in iOS Settings → returns to Fit33 → app relaunches (iOS killed the suspended process while the Settings deeplink was foreground) → `currentStep` reset to 0 → `restoreFromCheckpoint()` skipped because `isAuthenticated == true` → user landed on the login/signup screen with no path back. Behavior contract: leaving the app and returning normally MUST resume; force-quitting OR deleting the app MUST start over. The `UserDefaults` checkpoint key (managed by `OnboardingSessionManager.shared.startNewSession()`) is the single source of truth — `startNewSession()` runs first in `onAppear`, then `restoreFromCheckpoint()` reads it. NEVER add an additional `isAuthenticated`-style gate; if the user genuinely needs to start over (force-quit / fresh install), the checkpoint will already be cleared by `startNewSession()`'s session-id mismatch logic.
28-sync-d. **Onboarding profile photo MUST upload at the moment of selection (step 12), NEVER deferred to "Create Account" (step 15).** `Fit33/NewOnboardingView+Social.swift::processOnboardingPhoto` resizes the image to 300px max, sets `profilePhotoImage` state, then immediately fires `Task { await uploadOnboardingProfilePhoto(scaledImage) }` — uploading to Supabase Storage AND updating `user_profiles.profile_photo_url` in the same Task. Friend requests can be sent from steps 13-14 (contact sync screens), so a photo selected on step 12 but uploaded only on step 15 produces friend-request cards on the recipient's device that show the default monogram instead of the photo (canonical incident 2026-04-27). `Fit33/OnboardingPhotoPickers.swift::OnboardingPhotoPicker` was refactored from `@Binding` to `(UIImage) -> Void` callback so the library and camera paths both funnel through `processOnboardingPhoto` — when adding a new photo entry point during onboarding (e.g. crop sheet), wire it through the same callback so the eager-upload contract holds. The "Create Account" step MUST treat the upload as already-done — calling `uploadOnboardingProfilePhoto` a second time from `completeOnboarding()` would replace the URL and is a no-op for correctness but wasteful; `profilePhotoURL` state already carries the public URL set by step 12's upload, so the create-account RPC just reads it. NEVER move the upload back to `completeOnboarding` even if it "feels" cleaner — the friend-request card invariant depends on this timing.
28-sync-d-community-join. **`CommunityChallengeService.joinChallenge` and `joinChallengeFriendGated` MUST call `await syncAllTrackingToCommunityChallenges()` immediately after `await fetchMyChallenges()` — never assume the 1v1 → community fanout will populate today's row for a fresh joiner.** `community_challenge_daily_progress` is normally written by a server-side trigger that fans out from `challenge_daily_progress` (1v1) writes; the resulting row's `source` column is the literal string `"fanout:challenge_daily_progress"`. The trigger only fires for community challenges the user is a member of AT THE TIME of the 1v1 write, so a user who joins a community AFTER their app already pushed today's 1v1 progress will appear in the leaderboard as "—" until their NEXT foreground sync forces a fresh `challenge_daily_progress` row (which then fans out, retroactively populating today's community row). Canonical incident 2026-04-28: Manuel joined "10K Steps Daily" community at 03:16 UTC; his app had pushed 6,254 steps to `challenge_daily_progress` for the 1v1 vs Joe at 02:31 UTC; fanout did not replay → Manuel showed 6,254 in the 1v1 widget but "—" in the community leaderboard for the same calendar day. Fix: both join paths now call `syncAllTrackingToCommunityChallenges()` after `fetchMyChallenges()` — this writes today's HK steps directly via `log_community_challenge_progress` (independent of any 1v1 challenge state, so it works even for users with NO 1v1 challenge at all). NEVER drop the post-join `syncAllTrackingToCommunityChallenges()` call — the 1v1 fanout is not a substitute. NEVER reverse the order (sync first, fetch second) — `myChallenges` must contain the just-joined challenge before `syncAllTrackingToCommunityChallenges()` iterates. If a future join entry point is added (deeplink, share-sheet, push tap), it MUST follow the same pattern: RPC → `fetchMyChallenges` → `syncAllTrackingToCommunityChallenges`.
28-sync-d-deadlock. **`ChallengeService.backfillTodayProgressForChallenge` and `ChallengeService.syncHealthKitDataToChallenges` MUST call `HealthKitService.shared.refreshTodayStats()` — NEVER `HealthKitService.shared.syncAllData(force: true)`.** `syncAllData(force:)` is wrapped in `RequestCoalescer.coalesceVoid(key: "HealthKit.syncAllData.force=true")`, and its body chains into `await ChallengeService.shared.syncHealthKitDataToChallenges()` (line 234 of `HealthKitService.swift`). If `syncHealthKitDataToChallenges` then calls `syncAllData(force: true)` recursively, the coalescer joins the inner call to the outer (still-in-flight) Task — and the chain DEADLOCKS forever (outer awaits inner; inner awaits outer's `.value`). The Swift Task system does not detect this; the chain hangs until the parent Task is cancelled (e.g. user navigates away). Canonical incident 2026-04-28: Joe ↔ Paul 10K Club challenge `742c0bd0` — `backfillTodayProgressForChallenge` was first introduced calling `syncAllData(force: true)`, both call sites (the `respondToChallenge` accept path AND the `RealtimeService.handleAllParticipantUpdates` "opponent accepted" branch) silently hung at the first `await`, NEVER reaching `calculateTotalProgressFromAllSources` or `logProgress`. Paul's progress eventually appeared (multi-second delay) only when Joe navigated away from the challenge detail view, breaking the deadlock and letting a different code path catch up. Fix: `HealthKitService.refreshTodayStats()` is a lightweight entry point that only refreshes today's HK counters (`syncTodayStats`) — no TaskGroup, no chained challenge sync, no coalescer. NEVER replace `refreshTodayStats()` with `syncAllData(force: true)` inside `ChallengeService` — the deadlock will return for ALL outside callers of `syncAllData(force: true)`. NEVER add `await ChallengeService.shared.syncHealthKitDataToChallenges()` inside any new entry point reachable from `_syncAllDataBody`'s post-sync chain — same recursion shape will deadlock.
28-sync-d-accept. **Both participants of a 1v1/group challenge MUST write a `challenge_daily_progress` row IMMEDIATELY at accept time — neither side may rely on the other's logProgress to populate their row.** `Fit33/ChallengeService.swift::syncExistingProgressOnAccept` resolves `(challengeType, targetUnit, dailyTarget)` from `inviteDetails` (always present on the accept path — captured BEFORE the accept RPC fires) NOT from `activeChallenges.first(where:)`. The earlier `activeChallenges` lookup was throttle-sensitive: `fetchMinInterval` is 1.0s, and the realtime `handleParticipantStatusChange` "I accepted" branch fires its own `throttledChallengeFetch()` the same instant the participant row flips to `accepted` — racing the in-line `await fetchActiveChallenges()` in `respondToChallenge`. When the throttle won, `activeChallenges` was stale, the `first(where:)` returned nil, the function logged "Could not find accepted challenge in active list" and returned WITHOUT writing a row → both client widgets showed "—" for the opponent until the next foreground HK sync. Symmetrically, `Fit33/RealtimeService.swift::handleAllParticipantUpdates` "Opponent ACCEPTED my challenge" branch MUST call `ChallengeService.shared.backfillTodayProgressForChallenge(...)` on the SENDER's side after the refetch — without it, only the accepter's row landed and the SENDER's row never landed until their next foreground HK sync (canonical incident 2026-04-28: Joe ↔ Paul 10K Steps Daily Steps challenge `4076da0d` — Paul shipped 7,145 steps to `community_challenge_daily_progress` for the unrelated community 10K challenge but ZERO rows existed in `challenge_daily_progress` for the 1v1; Joe and Paul each saw their own value via `ActiveChallengeWidgetBridge.publishOptimisticLocalProgress` local-HK patching but each saw the opponent as "—"). NEVER re-introduce the `activeChallenges.first(where:)` early-return inside `syncExistingProgressOnAccept` — invite metadata is the deterministic source. NEVER drop the sender-side backfill from the realtime "opponent accepted" handler — server-side accept_challenge RPC does NOT log progress, and the sender's app is the only client that owns the sender's HK data. The sender-side handler MUST also retry `activeChallenges.first(where:)` ONCE via `ChallengeService.shared.forceFetchActiveChallenges()` (bypasses the 1.0s `fetchMinInterval` throttle; `RequestCoalescer` still dedupes any in-flight RPC) when the first lookup misses — the preceding `throttledChallengeFetch()` has a 3.0s throttle that reliably bails on a freshly-foregrounded app (the foreground 10-fan-out just ran <3s earlier), so without the retry the sender backfill silently skipped on every 1v1 acceptance after a fresh launch (canonical 2026-04-28 incident: 10K Club `742c0bd0` — Paul saw "0 steps" on his widget for multiple seconds after Joe accepted because his sender-side backfill silently bailed on the throttled lookup miss).
28-sync-e. **`ContactsService.canAccessContacts` MUST return `true` for `CNAuthorizationStatus.limited` on iOS 18+.** `Fit33/ContactsService.swift::canAccessContacts` uses `if #available(iOS 18.0, *) { return authorizationStatus == .authorized || authorizationStatus == .limited }` else `.authorized`-only. iOS 18 introduced `.limited` ("user picked specific contacts to share") as a third return value alongside `.authorized` / `.denied`; `fetchContactsAndFindFriends()` aborts with a guard on `canAccessContacts` so a `false` here silently drops every limited-access user with zero error UI.
