## Invariants (DB-specific — will cause data bugs / IDOR / crashes if violated)

### Type safety
1. **UUID type safety.** NEVER use `?? ""` as a fallback for `currentUser?.id.uuidString` in Supabase queries. Always `guard let userId = currentUser?.id else { return }`. Passing empty string to a UUID column causes Postgres `operator does not exist: uuid = text`.
2. **DTO null safety.** Every nullable DB column → Swift `Optional` in the DTO. Safe accessors with defaults (`opponentDisplayName: String { opponent_name ?? "Unknown User" }`).

### Pagination + duplicate fetches
3. **All Supabase fetch queries MUST include `.limit()`.** `fetchWorkoutHistory()` caps at 200; `fetchMealLogs()` caps at 100. Unbounded fetches cause memory spikes proportional to user history.
4. **No duplicate foreground fetches.** Centralized in `Fit33App.swift` scenePhase handler. `DashboardView` only handles dashboard-specific work (meals, hydration, quests). Never duplicate social/challenge/health fetches between App and Dashboard.
4a. **Wearable `force` flag MUST propagate through `HealthDataService.syncAllHealthData(force:)` to per-source methods** (`syncWhoopData(force:)`, `syncOuraData(force:)`, `syncFitbitData(force:)`). Each wearable service has its own 5-min `syncThrottleInterval`, so a top-level force that stops at HDS silently no-ops downstream — pull-to-refresh and scenePhase force syncs appear to do nothing. Fixed 2026-04-22.
4b. **Wearable widget staleness on tab return** is handled in `MainTabView.onChange(of: selectedTab)`: when returning to Dashboard (tab 0), if `WhoopService.shared.lastSyncDate` / `OuraService.shared.lastSyncDate` is >60s old, trigger a fire-and-forget force sync. Service-level `isSyncing` guard coalesces with any in-flight foreground sync. Never move this into `DashboardView.onAppear` — violates invariant #4.
4c. **WHOOP + Oura MUST be refreshed in `BackgroundChallengeSyncService.performSyncBody()`.** Both are OAuth pulls (not HealthKit writers), so without a BGTask refresh they go stale whenever the app is closed for any length of time — the Dashboard widget would show yesterday's recovery/strain/sleep on next open until the foreground Task finished syncing. Step 3b calls `WhoopService.shared.syncAllData(force: true)` (if connected), Step 3c calls `OuraService.shared.syncAllData(force: true)`. Step 3d then calls `ReadinessService.shared.recompute(force: true)` so today's blended readiness row also lands in `daily_readiness_history` from background (invariant #33 guarantees `recompute` does not recurse into wearable syncs). The scenePhase `.active` branch in `Fit33App.swift` also force-syncs both wearables in parallel with the main coordinated Task so the widget reflects live data the instant the user opens the app — the in-app service's own `isSyncing` guard coalesces the two paths when iOS just woke us.
4c-cache. **Wearable hero state on the dashboard MUST be `UserDefaults`-backed end-to-end — every `@Published` the widget reads.** `WhoopService` caches `todayRecovery` (`whoop_today_recovery`), `todayStrain` (`whoop_today_strain`), and `lastSleep` (`whoop_last_sleep`); `OuraService` caches `todayReadiness` / `todayActivity`. Every cached property MUST be (a) written in its `fetch*` method, (b) hydrated in `loadCachedDataIfNeeded()`, (c) cleared in `disconnect()`. Forgetting any one of those three steps for any one property produces a half-empty WHOOP/Oura card on cold start: the cached props render instantly, the un-cached prop sits at `--` until the next API call resolves — and if WHOOP hasn't yet scored last night's sleep at app open (8 AM cold start, recovery/strain already SCORED but sleep `PENDING`) the user sees `SLEEP --`, `ASLEEP --`, `EFFICIENCY --`, `RESP --` even though they're connected. Canonical fix: 2026-04-27 added `whoop_last_sleep` after the user reported the partial-card symptom; previously only recovery + strain were persisted. When you add a new `@Published` property the dashboard widget reads, follow all three hooks in the same PR. Also: any `result.records.first(where:)` selection from a paginated WHOOP/Oura response MUST sort by start descending first — public docs say newest-first, but a single ordering quirk would otherwise stick the dashboard on a 7-day-old record.
4d. **OAuth refresh-token rotation MUST be conditional on the server actually sending a new token.** Applies to `WhoopService.refreshAccessToken()` + `OuraService.refreshAccessToken()` (WHOOP and Oura both decode `refresh_token` as `String?`). Correct pattern: `if let rotated = tokenResponse.refreshToken, !rotated.isEmpty { refreshToken = rotated }`. The `refreshToken` keychain-setter deletes the stored entry when given `nil`, so an unconditional `refreshToken = tokenResponse.refreshToken` WIPES the refresh token any time the provider declines to rotate (WHOOP/Oura rotate on their own schedule, not on every refresh). The symptom is a zombie "connected" state — `isConnected == true` but every API call silently fails because `ensureValidToken` can't refresh an expired access token without a stored refresh token, and the `isConnectionError` catch branches in `fetchRecovery` / `fetchCycles` / `fetchSleep` / `fetchWorkouts` swallow the error to debug-log level. User-visible fix was manual disconnect + reconnect.
4c-supabase-integration-additive. **Bulk integration-status sync MUST be additive for OAuth services — never push `false`.** `SupabaseManager.syncAllIntegrationStatuses()` runs on every app launch; the OAuth columns it writes (`is_whoop_connected`, `is_oura_connected`, `is_strava_connected`, `is_fitbit_connected`) MUST only be set to `true` from this path (`local ? true : nil` pattern; nil → omitted from PATCH). The ONLY canonical `false` writers for OAuth integrations are the explicit user-action paths inside each service's `disconnect()` (the per-service `updateIntegrationStatus(integration:isConnected:false)` call). Rationale: iOS keychain entries for OAuth tokens are not guaranteed to survive app uninstall/reinstall (post-iOS-10.3 behavior is variable per-service per-device — observed in production logs as same-launch divergence: Strava token survived a reinstall while WHOOP + Oura tokens were wiped on the same launch). Pushing the empty-local state to Supabase destroyed the cloud signal "user has WHOOP/Oura linked at least once," which corrupted Bug Intel + analytics rollups, prevented any "tokens cleared on reinstall — tap to reconnect" UI prompt because cloud agreed with empty local before the UI rendered, and misrouted silent-push / edge-function targeting that gates on `is_<service>_connected`. Empty local state is not proof of user intent to disconnect. Apple Health (`is_apple_health_connected`) + InBody (`is_inbody_connected`) DO push their actual local state from the bulk path — Apple Health is HealthKit runtime auth (legitimately can revoke per-launch via Settings), InBody is BLE pairing (similar). Canonical fix: 2026-04-27 in `SupabaseManager.syncAllIntegrationStatuses()`.
4d-singleflight. **`refreshAccessToken()` MUST be single-flight — never let concurrent callers each fire their own POST `/oauth/token`.** Applies to ALL four OAuth services: `WhoopService`, `OuraService`, `StravaService`, `FitbitService` (all four shipped 2026-04-28). Canonical pattern in each file: a `private var refreshTask: Task<Void, Error>?` + a wrapper that returns the in-flight task's `.value` if one exists, otherwise spawns a new Task whose `defer` clears `refreshTask`. The actual network refresh body lives in `_performTokenRefresh()`; `refreshAccessToken()` is now ONLY the single-flight gate. Any future OAuth service (Garmin, Polar, etc.) MUST follow the same pattern. Rationale: `syncAllData(force: true)` is invoked from THREE foreground call sites in parallel on every cold start (`Fit33App.scenePhase .active` ✕ `MainTabView.onChange(of: selectedTab)` returning to Dashboard ✕ `BackgroundChallengeSyncService.performSyncBody`), and `force: true` BYPASSES the `isSyncing` guard. Inside one `syncAllData`, a `withTaskGroup` fans out 5 fetches that each call `apiRequest` → `ensureValidToken` → `refreshAccessToken` if the access token is within its 5-minute pre-expiry window. With no coalescing, ≥10 concurrent POSTs to WHOOP / Oura `/oauth/token` race with the SAME `refresh_token`. Both providers single-use refresh tokens: the first POST rotates RT_1 → RT_2, every subsequent POST gets HTTP 400 `invalid_grant`, the 400 branch in `_performTokenRefresh` calls `disconnect()` (correctly, for a real revoke — but every replay-race victim ALSO trips it), tokens are wiped, `is_whoop_connected = false` is PATCH'd to `user_profiles`, and the user has to manually reconnect on every app launch. Canonical incident: 2026-04-28 — Joe reported "I have to resync WHOOP almost every login," DB confirmed `is_whoop_connected: false` + `is_oura_connected: false` for his profile despite valid grants. Single-flight collapses N concurrent refreshes into ONE POST; awaiters share the same outcome. Zero extra network traffic, zero replay rejections, zero false disconnects. NEVER call `_performTokenRefresh` directly from `apiRequest` / `ensureValidToken` / a 401 retry — always go through the `refreshAccessToken()` single-flight wrapper. NEVER make the `refreshTask` clear path async (`Task { @MainActor in ... }` wrapper inside `defer`) — the enclosing `Task<Void, Error>` already inherits @MainActor isolation; a nested Task can race the next caller's nil-check. NEVER convert this to a semaphore / lock — Swift Concurrency Task-based coalescing is the canonical pattern (matches `RequestCoalescer` and the sync-triage Layer A.2 fan-out).
4d-recover. **Wiped refresh tokens MUST auto-recover, not zombie-stay-connected.** Once `refreshAccessToken()` is invoked it MUST disambiguate "keychain transiently locked" (BGTask wake on a locked device — both `accessToken` and `refreshToken` keychain reads return `nil`, retry next foreground) from "refresh token genuinely wiped" (`accessToken` reads succeed but `refreshToken` is `nil` — permanent). Canonical probe: `let keychainReadable = KeychainHelper.load(key: "<service>_access_token") != nil` inside the `guard let currentRefreshToken = refreshToken else { ... }` branch — if `keychainReadable == true` and `refreshToken == nil`, call `disconnect()` and set `errorMessage` to a reconnect-prompting copy so Settings + the dashboard widget switch back to the "Sync <service>" reconnect CTA. Without this auto-recover, the zombie state from invariant 4d is permanent — the user sees a connected status, "Sync now" returns no data, every endpoint debug-logs `"skipped: not connected"`, and the only way out is a manual Disconnect tap they have no signal pointing toward. Logs confirming this state: 4-5 consecutive `[<SERVICE>] refreshAccessToken: no stored refresh token (keychain locked?)` warnings followed by `Recovery / Cycles / Sleep / Workouts skipped: Not connected to <SERVICE>` debugs in the same sync pass while `[INTEGRATIONS] ... <SERVICE>: true` reports the integration as connected. Canonical fix: 2026-04-27 in `WhoopService.refreshAccessToken()` + `OuraService.refreshAccessToken()`. NEVER bypass this by `disconnect()`-ing on every nil read — that re-introduces the original "spontaneously disconnected after every TestFlight update" bug 4d's defensive throw was protecting against. The accessToken-readable probe is what makes both safe. When refresh fails (HTTP non-200 OR missing stored refresh token) the service MUST call `disconnect()` before throwing so the UI surfaces the reconnect prompt instead of silently showing stale data. Strava/Fitbit decode `refresh_token` as non-optional `String`, so a missing field raises a decode error and can't silently wipe — if you ever relax those to optional, carry this pattern over. Canonical fix: 2026-04-24 in both services. Mirrors the `exchangeCodeForTokens` `if let rt = … { refreshToken = rt }` pattern that was already correct on the initial-authorization path.

### Security (RPCs + views + edge functions)
5. **RLS on every user-data table** — `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + CRUD policies scoped to `user_id = auth.uid()`. (Also in `codingrules.mdc`.)
6. **Views use `security_invoker = on`.** Never `SECURITY DEFINER` on views in `public`. (Also in `codingrules.mdc`.)
7. **RPC IDOR prevention (MANDATORY).** Every `SECURITY DEFINER` RPC taking a user-id-like parameter (`p_user_id`, `user_id_to_delete`, …) MUST either:
   1. Drop the parameter entirely and use `auth.uid()` (preferred), OR
   2. Guard at the top:
      ```sql
      IF auth.uid() IS NOT NULL AND p_user_id <> auth.uid() THEN
          RAISE EXCEPTION 'Forbidden' USING ERRCODE = '42501';
      END IF;
      ```
   `auth.uid() IS NOT NULL` lets service-role / pg_cron callers through. Canonical: `supabase/20260417_secure_get_friend_ids.sql`.
8. **Edge function CORS.** Import `buildCorsHeaders(req)` from `supabase/functions/_shared/cors.ts`. Never ship `Access-Control-Allow-Origin: *`.
9. **Every new edge function goes into the Edge Function Auth Registry in `INFRA_SECURITY_AGENT.md` in the same PR.**
10. **Edge function input validation at entry point.** Zod or manual. Standard error response: `{ error: string, code: string }`. Never log full phone numbers, auth tokens, or PII.

### Contracts with Swift
11. **Return-type contract with Swift.** SQL `RETURNS jsonb` → Swift decodes a `Decodable struct`, never `Bool`. SQL `RETURNS boolean` → `Bool`. If you change a RETURNS clause, grep the RPC name in `Fit33/SupabaseManager.swift` and all `*Service.swift` and update decoders in the same commit.
12. **SQL `RETURNS TABLE` functions:** set `#variable_conflict use_column` at the top if any parameter name collides with a column name (hard-won 2026-03-29).
13. **SQL RECORD types** — never use anonymous `ROW(0,0,0)` to init a `RECORD`; the fields have no names. Use `SELECT 0 AS field_name, ... INTO v_record` instead.

### Social + moderation
14. **Moderation flip propagates via realtime.** The moderation webhook sets `is_hidden = true` after insert. Any client UI that persists the sender's own row (chat, activity feed) MUST subscribe to `UpdateAction` on that table and drop rows where `is_hidden` flipped true. Canonical: `RealtimeService.subscribeFriendActivityFeed` + `PrivateChallengeService` UPDATE sub. Server RPCs filter hidden rows, but local caches don't refresh without this.
15. **Legacy `group_challenge_members` is revoke-hardened.** RLS enabled; `INSERT/UPDATE/DELETE` revoked from `authenticated`, `ALL` revoked from `anon`. Only `service_role` + SECURITY DEFINER RPCs may write. Use `challenge_participants` for the live challenge system. See `supabase/20260418_group_challenge_members_invariant.sql`.
16. **Social compliance RPCs.** `get_blocked_users()` and `report_content(p_table_name, p_record_id, p_reported_user_id, p_content_snippet, p_reason)` are the canonical App Review compliance surfaces. `report_content` hard-filters `p_table_name` against an allowlist: `private_challenge_chat`, `challenge_reactions`, `shared_workouts`, `group_challenges`, `private_challenges`, `community_challenges`, `friend_activity_feed`, `user_profiles`. Writes to `content_moderation_log` with `flagged_categories=["user_report"]`.

### Realtime
17. **CMS exercise edits flow through realtime.** Saving an exercise in `admin.doublethr33s.com` fires `public.exercises` Realtime → `RealtimeService.subscribeExercises()` → `ExerciseLibraryService.upsertExerciseFromCloud(dto)`. **NEVER** call `forceSyncExercises()` in response (1000× more expensive; wipes Core Data). CMS also fires `rpc('refresh_mv_public_exercises')` so cold starts (which read `mv_public_exercises`) pick up the change. Requires `exercises` in `supabase_realtime` publication with `REPLICA IDENTITY FULL` (`supabase/20260420_exercises_realtime.sql`).

### Exercise performance history — single canonical writer (2026-04-27 — hard-won)
17b. **`ExerciseHistoryService.saveExercisePerformance()` is the SINGLE canonical writer for `exercise_performance_history`.** Invoked from `ActiveWorkoutView+Persistence.saveExercisePerformanceHistoryWithData()` (called by the active-workout completion path with captured sets data, race-safe vs. `WorkoutManager.exerciseSetsData` clear). Populates `total_reps`, `max_weight`, `max_reps`, `avg_weight`, `avg_reps`, `total_volume`, `total_sets`, `workout_duration_seconds`, `had_failure_set`, `had_dropset`, plus per-set rows in `exercise_set_history`, plus `updatePersonalRecords` → `exercise_personal_records` upsert. The `RecentSessionsTilesRow` tile row above the active-workout exercise card reads `avg_weight` via `ExerciseHistoryService.fetchRecentSessions(for:limit:)`; ANY parallel writer that leaves `avg_weight` NULL renders as a `— lb · <date>` ghost chip beside the real one — looks like the user logged the same workout twice. Until the 2026-04-27 cleanup, `WorkoutManager.recordExercisePerformance()` was a second writer that populated only the legacy `best_set_*` / `one_rep_max_estimate` / `equipment_used` columns and produced exactly that ghost-chip symptom (256 / 611 rows on prod were duplicates across 3 affected users). Removed from `Fit33/WorkoutManager.swift::completeWorkout`; cleanup migration `supabase/20260704_dedupe_exercise_performance_history.sql` deletes phantom rows where a canonical sibling exists for the same `(user_id, exercise_name, workout_id)`. **NEVER** re-introduce a parallel writer here. The legacy columns (`best_set_weight`, `best_set_reps`, `one_rep_max_estimate`, `equipment_used`) remain in the schema for backwards-compat with historical legacy-only rows but are NOT read by any current Swift surface — if you find yourself wanting to populate them, write the equivalent via the canonical writer's `total_volume` / `max_weight` / `max_reps` columns instead. Reinforces the existing "Exercise performance table: columns are `max_weight` / `max_reps` (NOT `best_set_*`)" key established rule.

### RPC ↔ schema column read invariant (2026-04-27 — latent-bug class)
17c. **Every column referenced inside a `SECURITY DEFINER` RPC body MUST exist on the target table from the SAME migration that introduces the read.** Conditional-branch reads (`IF v_x THEN SELECT col INTO v ... FROM tbl ...`) are especially dangerous: the column-missing error stays hidden as long as the gate stays `FALSE`. Canonical incident: `user_daily_quests.bonus_claimed` was referenced by every `get_daily_quests` overload from `20260324_adaptive_quest_selection.sql` forward (current head: v4 in `20260703_get_daily_quests_brief_signals.sql`) but the original `daily_quests_migration.sql` `CREATE TABLE user_daily_quests` shipped without the column. The bug stayed dormant for 8 months because the SELECT was gated on `IF v_all_complete THEN` — CI fixtures never completed all 3 daily quests. The instant a real user finished their last quest of the day, every subsequent dashboard refresh raised PostgreSQL 42703 (`column "bonus_claimed" does not exist`) and the slate collapsed to `defaultGoals()` until midnight (bug-intel fingerprints `76860b32`, `8e0764bf`, `4729e709`, `537be0ee` — 22 occurrences, build 1.38(59), all on 2026-04-27). Closed by `supabase/20260707_user_daily_quests_bonus_claimed.sql`. **Authoring rule**: when you `git grep` an RPC's `SELECT <col>` patterns, EVERY column on the LHS or RHS must trace to a `CREATE TABLE` or `ADD COLUMN IF NOT EXISTS` in a migration that runs at-or-before the RPC body migration — not "should exist eventually," from the same PR. The pre-commit migration check should fail any new RPC that references a column not present in `information_schema.columns` snapshot.

### Edge function error wrapping in `supabase-functions-swift` (2026-04-27)
17d. **`FunctionsError.httpError(code:data:)` collapses non-2xx responses to `"Edge Function returned a non-2xx status code: <code>"` — the response body is unreachable from `.localizedDescription`.** Any `NetworkErrorClassifier` body-string pattern (e.g. `"forbidden: new_user_id must match caller"`) MUST therefore also be matched at the call site BEFORE classification, OR the classifier-bypass `.error` log will create a bug-intel fingerprint per occurrence. Canonical incident: `Fit33/ContactsService.swift::notifyExistingUsersOfNewJoin` 403 → IDOR guard race during `auth.signUp` JWT propagation. The classifier already had the body-string pattern but never saw the body, so every onboarding flow created fingerprints `b242269c`, `65f3c668`, `1951d472`. Pattern (verified canonical): catch the bare `"non-2xx status code: 403"` at the call site, log at `.debug`, fall through to the classifier ONLY for unexpected status codes. Applies to any iOS-side `.functions.invoke()` whose edge function uses an IDOR guard — `notify-contacts-user-joined`, future `claim_*` RPCs, etc.

### Migrations
20. **Migration naming:** `YYYYMMDD_HH_description.sql` (or `YYYYMMDD_description.sql`). Always wrap in `BEGIN; ... COMMIT;`. Always idempotent (`IF NOT EXISTS`, `DROP ... IF EXISTS` before `CREATE`). Add every migration to `supabase/MIGRATION_INDEX.md` in the same PR.

### Schema lessons
21. **Never drop tables with active writers.** `crash_reports` was dropped (0 rows at audit) but `CrashReportingService.swift` writes on every error. Always grep the codebase for table references before dropping.
22. `user_push_tokens` requires `UNIQUE(user_id, device_token)` — `onConflict` in `PushNotificationService.swift` depends on it.
23. `collaborative_workout_data` has `user_equipment JSONB` (`20260321_schema_fixes.sql`).

### Supabase Swift client — UUID handling
24. **Pass Swift `UUID` directly to `uuid` columns — NEVER `uuidString` / `String`.** Applies to `.insert()`/`.upsert()` struct fields AND `.eq()` filter values. The Supabase Swift client's `Encodable` conformance serializes `UUID` correctly; passing a `String` causes a type mismatch at the PostgREST boundary. Same-bug repeat offenders: `WeightTrackingService.setWeightGoal`, `logWeight()` — both fixed; don't regress.

### DTO null-safety (reinforces #2)
25. **Integer columns without `NOT NULL DEFAULT` → `decodeIfPresent` + safe default in Swift.** Never assume a DB integer is non-null. Pattern:
    ```swift
    self.reps = try container.decodeIfPresent(Int.self, forKey: .reps) ?? 0
    ```
    Missing a default produces silent decoder failures that drop the entire row.

### Auth-guarded writes
26. **Every Supabase INSERT / UPDATE / DELETE / UPSERT / RPC call MUST check `SupabaseManager.shared.isAuthenticated` first.** `currentUser?.id` is insufficient — a user object can persist in Core Data with an expired Supabase session. Missing this guard caused 9 errors across 7 analytics tables during a single workout save (v1.34). Log guarded skips at `.warning` with category `.auth`.

### Workout save idempotency (calorie patch path)
27. **Never re-save the full workout from the calorie write path.** `ActiveWorkoutView+Persistence.saveWorkoutToAppleHealth()` patches the single `calories_burned` column via `SupabaseManager.updateWorkoutCalories(workoutId:calories:)` — a targeted `.update(["calories_burned"])`. Calling `saveWorkoutToCloud(workout:)` from here (as in v1.34) creates duplicate rows because the primary sync path in `saveWorkoutData()` already saved the workout.

### HealthKit / Strava dedup
28. **NEVER re-introduce `if workout.isFromStrava { continue }` in `HealthDataService`.** The skip was added during a dedup experiment and permanently dropped Strava-via-HealthKit runs for users who don't have Strava OAuth connected. Dedup must happen via the cardio overlap key (`canonical_origin`, see `SUPABASE_AGENT.md` WHOOP/cardio dedup rules), not by skipping a source wholesale.

### Strava integration upgrade (2026-04-25)

Service-role-only lookup `get_user_id_for_strava_athlete(p_athlete_id)` maps the Strava `owner_id` in webhook payloads back to the app `user_id` without exposing the table to anon.

Only fired on `aspect_type='create'` events — `update` events are noisy (kudos count changes) and would spam the carousel. - Views use `@Environment(\.managedObjectContext)` — never `PersistenceController.shared.container.viewContext` directly.
- Context-safety rules (singleton caches, `Task { }` vs `Task.detached`, `bgContext.mergePolicy`, DEBUG `assertContext` guard) live in `.cursor/rules/codingrules.mdc`.

## Key Established Rules
- **Strava sync:** `max(stored, incoming)`, never add.
- **Exercise performance table:** columns are `max_weight` / `max_reps` (NOT `best_set_*`).
- **`WeightTrackingService`** is the single source of truth for user weight.
- **Phone matching MUST be server-side** via RPC.
