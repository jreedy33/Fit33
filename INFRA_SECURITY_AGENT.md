## Invariants (Infra/Security-specific — will leak data / break auth if violated)

### Secrets
1. **Secrets.swift is the ONLY source** for every third-party client ID, client secret, API key. `Secrets.swift` is gitignored. `Secrets.template.swift` is committed with `<PLACEHOLDER>` values and lists every expected key.
2. **No literal credential fallbacks in `AppConfig.swift`.** If `Secrets.swift` is missing, the build fails — that is the intended behavior.
3. **OAuth tokens → Keychain** via `KeychainHelper.swift`, never UserDefaults (Strava, Fitbit, WHOOP, InBody).

### Edge Function auth (MANDATORY; see Registry below)
4. Every new edge function MUST be added to the Edge Function Auth Registry below in the same PR.
5. **`verify_jwt: true` is the Supabase default.** A missing `Authorization` header is rejected by the platform BEFORE function code runs (`{"code":"UNAUTHORIZED_NO_AUTH_HEADER"}`). Custom headers (`x-cron-key`, `x-moderation-secret`) are NEVER sufficient on their own — caller must also send a valid `Authorization: Bearer <JWT>` (service-role for server-to-server, user JWT for iOS). When probing, always test BOTH with and without the custom secret to verify your code path actually runs.
6. **CORS is centralized.** Import `buildCorsHeaders(req)` from `supabase/functions/_shared/cors.ts`. Never `Access-Control-Allow-Origin: *`.
7. **PII redaction in edge logs.** Phones → `redactPhone()` in `supabase/functions/_shared/log.ts` (`+1***-***-1234`). Emails → `j***@gmail.com`. Auth tokens, passwords, payment data → never logged.
8. **"Auth-present" ≠ "auth-correct".** Always ask what bound identity the handler enforces. If the endpoint is cost-sensitive (Twilio / OpenAI / Anthropic) or privileged (`generate-ai-insights`), accepting any valid user JWT is insufficient — use service role or an allow-list table.
9. **SECURITY DEFINER RPC IDOR guard.** Either drop the user-id parameter (use `auth.uid()`), or gate at top: `IF auth.uid() IS NOT NULL AND p_user_id <> auth.uid() THEN RAISE EXCEPTION 'Forbidden' USING ERRCODE = '42501';`. The `auth.uid() IS NOT NULL` clause lets service role / pg_cron through. Smart Adaptive Daily Goals RPCs (`reroll_daily_quest`, `claim_double_xp_day`, `submit_custom_quest`, `unsuppress_quest_category`, `verify_strava_quests_for_today`, `verify_wearable_quests_for_today`, migrations 20260606–20260607) all follow this pattern — they take no `p_user_id` and resolve the caller via `auth.uid()`, returning `{success: false, reason: 'not_authenticated'}` when null. The Pro RPCs additionally require caller-provided `p_is_pro=TRUE` (matches the existing `p_is_subscriber` pattern in `get_daily_quests`); a future migration will swap this for a server-side `is_subscriber()` read once the canonical premium column lands. New per-user tables `user_quest_personalization`, `user_quest_key_stats`, `user_activity_mix`, `user_quest_rerolls`, `user_double_xp_claims` are RLS-pinned to `auth.uid() = user_id` and added to `delete_user_account()` (Supabase invariant 3).
10. **Rate limits for cost-sensitive endpoints must be DB-backed.** In-memory limiters reset on every cold start (every few minutes). Canonical: `check_phone_verification_rate_limit` RPC. In-memory is fine only for abuse-prevention on free APIs.
11. **Never hardcode project refs.** Always `Deno.env.get('SUPABASE_PROJECT_REF')`.
11a. **New-format `sb_secret_…` keys get JWT-translated by the platform; verify against `payload.iss` AND `payload.ref`.** When a caller sends `Authorization: Bearer sb_secret_…` (the 2026 opaque secret-tier key format Supabase rolled out), the gateway translates the secret into a service-role JWT BEFORE it reaches the function. That translated JWT carries `role: "service_role"` BUT the project ref is in the `iss` claim (issuer URL `https://api.supabase.co/v1/projects/<ref>/api-keys-jwt-issuer`), NOT in the legacy `ref` claim. A function whose `isServiceRoleJWT()` only checks `payload.ref === EXPECTED_PROJECT_REF` will reject every new-format key with HTTP 403 even though the request is legitimately service-role — this is exactly how `audit-catalog-exercise` failed on first deploy until the fix landed (joe@2026-05-07). Canonical pattern (`supabase/functions/audit-catalog-exercise/index.ts::isServiceRoleJWT`):
```ts
if (payload.role !== 'service_role') return false;
if (payload.ref === EXPECTED_PROJECT_REF) return true;                                // legacy JWT
if (typeof payload.iss === 'string' &&
    payload.iss.includes(`/projects/${EXPECTED_PROJECT_REF}/`)) return true;          // new-format translated
return false;
```
Also accept `token.startsWith('sb_secret_')` as defense in depth at `resolveAuth()` — the platform has already validated the secret server-side before it reached us, so the prefix-match is a sufficient gate at the function layer (the only thing that could send `sb_secret_*` through `verify_jwt: true` is a legitimate secret-tier key). New edge functions added to the Registry MUST handle BOTH the legacy-`ref` and new-`iss`/`sb_secret_` paths, OR they'll silently fail the moment the operator rotates to the new key format. Probe: hit the function from a script that uses the actual `SUPABASE_SERVICE_ROLE_KEY` from `.env` (whatever format it's in) — if it 403s, you have a translation bug, not a key bug.

### Silent push + APNs
12. **Silent pushes MUST use `apns-priority: 5`.** APNs silently drops priority-10 silent pushes. Also: `apns-push-type: background`, `aps.content-available: 1`, `apns-expiration: ~+1h`.
13. **Silent pushes skip `push_notification_queue`.** That table is for user-visible alerts (retry + quiet hours). Silent pushes are opportunistic.
14. **Silent-push rate-limit records are internal.** `silent_push_wake_log` is service-role-only; never add a client-readable RLS policy.
15. **Silent-push handler time budget ~30s; per-type self-cap.** `SilentPushHandler.handle(userInfo:completion:)` runs an independent timeout `Task` per push type. Current caps: `strava_activity_new` 25s, `challenge_wake` **15s** (lite path). Exceeding the budget marks the result `.failed` and penalizes our future background-delivery allocation, so caps must be snug enough that timeouts surface real regressions instead of masking them.
15a. **`challenge_wake` runs the LITE path, not the full sync.** `SilentPushHandler.handleChallengeWake` calls `BackgroundChallengeSyncService.performLiteWakeSync()` — HealthKit `syncAllData(force: true)` (Data invariant #46) + `fetchActiveChallenges`/`fetchActiveGroupChallenges` (Data invariant #49) + `syncAllTrackingToChallenges` + private + community sync, ONLY. Strava/Fitbit/WHOOP/Oura/Readiness/meals/hydration/Quests/Intelligence cache stay on the foreground + BGAppRefresh + BGProcessing paths. Bundling them into the wake handler was the dominant timeout cause for users with multiple wearables connected, and none of them affect opponents' view of step / active-min / distance / calorie progress (those flow through HealthKit only — Strava-driven distance still updates because Strava writes to HealthKit). Lite path runs in ~3-7s in the field.
16. **Client-side silent-push calls debounce to 60s per device** (`ChallengeOpponentWakeService` actor). Guard on `(activeChallenges + activeGroupChallenges + privateChallenges).count > 0` and on `SupabaseManager.shared.isAuthenticated`.
17. **New silent-push types get their own case in `SilentPushHandler`.** Don't overload `challenge_wake`.
17b. **`silent_push_wake_log.triggered_by` is the per-source throttle bucket key.** Each `triggered_by` value (`foreground` / `cron` / `background_sync` / `progress_update`) gets its own throttle window in `wake-challenge-opponents/index.ts::THROTTLE_WINDOWS_MS_BY_SOURCE` — the lookup `WHERE triggered_by = source` ensures buckets don't suppress each other. `progress_update` is the **only sub-15-min bucket** (60s, Phase 7b 2026-04-26) and is reserved for the server-trigger fan-out from `notify_opponents_on_progress_change()` — adding new sources at <15 min must (a) extend the CHECK constraint on `silent_push_wake_log.triggered_by`, (b) add the bucket to the throttle map, and (c) require service-role auth at the edge function (a chatty user-driven 60s bucket would let any user spam any other user). Canonical migration: `supabase/20260625_opponent_progress_silent_push.sql`.

17c. **Interactive social pushes BYPASS `daily_cap` and `category_cap`.** `send-push-notification/index.ts` defines `INTERACTIVE_BYPASS_TYPES` — every notification type that fires because another user explicitly took an action targeting the recipient (`friend_request`, `challenge_invite`, `challenge_reaction`, `shared_workout`, `private_challenge_message`, etc.). Capping these breaks the social loop: the sender thinks it went through, the recipient gets nothing, and the sender (under the default `daily_cap = 8`) gets capped after 8 events even if every one was a friend tapping back at them. Adding a new interactive type? Add it to `INTERACTIVE_BYPASS_TYPES` in the same PR. Caps still apply to engagement nudges (`comeback_reminder`, `streak_*`, `challenge_nudge`, `daily_workout_reminder`, `morning_motivation`, `weekly_progress`, `*_goal`, `*_reminder`). A `cap_bypass` row is written to `push_notification_delivery_log` whenever the bypass fires — grep `event = 'cap_bypass'` if a user later complains about noise. Companion bug fixed in the same patch: `computeNextLocalMidnightUTC` was returning yesterday's local midnight for west-of-UTC zones (`localH > 12` was treated as a forward offset, dropping `tomorrowUtcGuess` 24h into the past); the wrap fix is `offsetHours = rawLocalH > 12 ? rawLocalH - 24 : rawLocalH`. The two bugs together produced an infinite re-defer loop — once a user hit the cap, every subsequent notification deferred to a past timestamp, which the cron picked up immediately and re-deferred (jreedy 2026-05-02: 30+ `cap_exceeded` events per second). Always test cap-deferred retry timestamps in BOTH a west-of-UTC and east-of-UTC TZ when touching this code.

17a. **Wake diagnostics RPC is the only client-readable surface for `silent_push_wake_log`.** `get_my_wake_diagnostics(p_lookback_hours INT DEFAULT 24, p_timezone TEXT DEFAULT 'UTC')` (migrations `supabase/20260618_wake_diagnostics_rpc.sql` (#118) + `supabase/20260619_wake_diagnostics_progress_drift.sql` (#121)) is `SECURITY DEFINER`, pinned to `auth.uid()`, and only returns wake-log + token + cross-table progress-drift rows for the caller and counterparts in their active 1v1 / group / private challenges. Lookback clamped to [1, 168] hours. Returns first 12 chars of newest valid `device_token` for visual matching only — never the full token. **Cross-table drift columns** (`steps_today_1v1` / `steps_today_private` / `steps_today_community` / `progress_drift_detected`) surface Data invariant #48 regressions directly in the dev menu (the trigger is currently deployed and healthy — verified 2026-04-26 — so the steady state is `progress_drift_detected = FALSE`; any TRUE means the fanout trigger has regressed). Built during the 2026-04-26 "Abbie 0 vs 603" investigation, which turned out to be an upstream sync delay rather than drift — these columns served as the disconfirmation tool. The DEBUG-only `WakeDiagnosticsView` (Fit33/WakeDiagnosticsView.swift, dev menu tab "Wakes") consumes this RPC. **Never** add a client-readable RLS policy to `silent_push_wake_log` itself (invariant #14 still holds); always extend this RPC instead. When extending the drift columns to other fanout types (`active_minutes` / `calories`), repeat the steps_today_* CTE pattern — never expose raw row dumps.

### Background services
18. **`BackgroundChallengeSyncService` throttling model**: per-source last-sync throttle (`perSourceThrottleInterval = 600s` / 10 min, stored under `bg_challenge_last_sync_<source>` in UserDefaults) prevents a single noisy HK source (steps) from starving the others. Workouts flagged high-priority bypass the throttle. BGAppRefreshTask is scheduled with `earliestBeginDate = +15 min`; BGProcessingTask with `+2h`. Concurrent callers coalesce on a single `@MainActor var inFlightSyncTask: Task<Void, Never>?` per QP invariant #24c. Every BGTask expiration handler MUST call `setTaskCompleted(success: false)` AND schedule the next cycle — leaving it dead stops BG wakes until next launch.
19. **`DailyResetService`**: runs at user's local midnight (not UTC). Must be idempotent.

### Info.plist required modes
20. `UIBackgroundModes` MUST include `remote-notification` (silent push) and `fetch` (BGAppRefresh). Missing either → iOS drops our background events.
21. `BGTaskSchedulerPermittedIdentifiers` MUST include every BGTask identifier the app schedules (current: BGAppRefresh id + `com.gofit.app.challengeSyncProcessing`).

### Realtime Widget Server Pull (2026-04-26)
21a. **Supabase session JWT now lives in the App Group, not `UserDefaults.standard`.** `Fit33/SupabaseAppGroupStorage.swift` implements `AuthLocalStorage` against `UserDefaults(suiteName: "group.com.fit33.app")` so the widget extension and the watch app can read the bearer token without re-implementing OAuth. **One-time migration** at app launch in `SupabaseManager.init()` reads any legacy session from `UserDefaults.standard` + Keychain, copies it into the App Group container, then deletes the legacy copy. Trade-off accepted: the App Group `UserDefaults` is sandbox-readable by any process signed with our team ID + `group.com.fit33.app` entitlement (i.e. our widget + watch apps only — NOT third parties). This is the same posture Apple recommends for shared session storage; it is acceptable because (a) the JWT is short-lived (24h max — Phase 7d bumped from 1h to 24h to support widget step write-back through a full app-vacation day), (b) refresh tokens are NOT persisted to App Group, (c) extensions never call refresh — they fail closed when the access token has expired and wait for the host app to refresh. NEVER persist refresh tokens or any other credential into the App Group container. **Phase 7d (2026-04-26) narrows but does not break the read-only invariant**: the widget extension MAY call `log_challenge_progress` with `p_source = 'widget'` and ONLY that — no other RPC, no auth-mutating call, no other write surface. The narrow allow-list lives in `RunningActivityWidget/WidgetSupabaseFetcher.swift::logChallengeStepProgress(...)`. Server-side kill switch (`internal_config.widget_writes_enabled`) silent-success no-ops widget-source writes — flip to `'false'` from the dashboard if the path ever misbehaves; the iOS code keeps trying but the server pretends it worked. Widget watches and other extensions MUST stay strictly read-only — no precedent here for adding more write paths without an explicit security review. Canonical migration: `supabase/20260626_widget_writes_kill_switch.sql`.
21b. **Engagement-nudge cron is service-role-only.** `enqueue_engagement_nudges_for_stale_opponents()` (migration #123, schedule `0 * * * *`) is `SECURITY DEFINER` with `GRANT EXECUTE ... TO service_role` — the anon role MUST NEVER be able to enqueue arbitrary `challenge_nudge` rows or attackers could spam any user. The function defers quiet-hours / master-enabled / disabled-type enforcement to `send-push-notification`, so user prefs still gate delivery even though enqueue is server-side. Throttle is enforced in SQL: 24h challenge warm-up, 12h staleness floor, 20h per-(recipient, challenge) — modifying these requires updating both the SQL and the QP test fixtures.

### Admin CMS
22. **Admin session tokens are httpOnly Secure SameSite=Strict cookies.** Never write a client-readable cookie for auth state. The one path middleware skips (`/`) is a server component that reads cookies via `next/headers` + `cookies()` + `redirect()`. Never add `document.cookie.includes(...)` back. Canonical implementation: `admin-cms/src/lib/auth-cookies.ts` (`COOKIE_OPTIONS`).
23. **CSP is set ONLY in `admin-cms/src/middleware.ts`.** Sprint 5 (Q2-20) moved to per-request nonce + `strict-dynamic`; `next.config.ts` intentionally omits `Content-Security-Policy`. When adding a new external media domain (e.g. an R2 bucket in `media-src`) update middleware only. Never re-introduce a static CSP header in `next.config.ts` — two sources fight and silently regress to `'unsafe-inline'`.
24. **R2 video URLs are raw filenames.** Never `encodeURIComponent` on filenames — they contain parentheses `(male)` / `(Dumbbell)` that break.
24a. **Login error responses MUST stay generic.** `/api/auth/login` returns `Invalid credentials` for BOTH "email not in `ADMIN_EMAILS` allowlist" AND "Supabase rejected password" — anti account-enumeration. Differentiate failure modes ONLY in server-side `console.warn('[auth/login] reject reason=...')` logs (visible in Vercel Logs). Canonical: `admin-cms/src/app/api/auth/login/route.ts`. Never leak the distinction to the client response, even on private deployments — the generic-error invariant is what makes brute-forcing emails uneconomical.
24b. **`ADMIN_EMAILS` ↔ Supabase user drift is detectable BEFORE lockout.** The CEO-lockout class on 2026-04-29 was: allowlist had `joe@doublethr33s.com`, but no `auth.users` row existed at that email. Run `npm run admin:audit` (script: `admin-cms/scripts/admin-audit.mjs`) from `admin-cms/` to verify every allowlist entry resolves to a Supabase user with verified TOTP. Run it whenever you add/remove admins, rotate keys, or change Supabase projects. The admin-gated `GET /api/admin/health` endpoint surfaces the same audit JSON in-CMS once logged in — NEVER make it public, it enumerates the admin allowlist.
24c. **Adding an email to `ADMIN_EMAILS` REQUIRES creating the matching Supabase auth user in the same change.** Use the admin REST endpoint (`POST /auth/v1/admin/users`) or follow `admin-cms/RECOVERY.md`. Allowlist drift is silent — the login route returns the same generic error for "no such user" as it does for "wrong password". A future agent MUST be able to discover the missing-user mode by reading server logs (`reason=SUPABASE_AUTH_FAILED supabase_error=...`) or running the audit script.

### New User Journey Tracking — privacy posture (Migration #167)
24d. **`new_user_journey_events.payload` MUST NEVER contain email / phone / full-name / IP / payment-token / bug-report free-text body.** The pipeline auto-enrolls EVERY new user for 72 h (no per-email allowlist like `dev_logging_users`), so payload hygiene is the only privacy boundary. Domain data IS allowed in payloads — food names, exercise names, search queries, screen names — those are product-search terms, not PII. Free-text bug-report bodies stay in `bug_reports`. Failed-auth credentials stay in GoTrue logs (we never see them). Apple-purchase tokens stay in `iap_receipts`. Adding a new tracker call (`NewUserJourneyTracker.shared.log*`) requires reviewing the payload shape; if a new field could carry PII (e.g. `event_payload["recipient_email"]`), redact at the call site BEFORE the tracker line. RLS on the events table only allows the user to read their OWN rows; reports are admin-only (no `authenticated` SELECT policy at all). Edge-fn `generate-new-user-report` runs service-role-only — never accept a user JWT. CMS surface (`/new-user-reports`) is gated by the existing `ADMIN_EMAILS` allowlist + TOTP. The `cleanup_new_user_journey_data()` cron drops events + sessions older than 30 days from `journey_started_at`; reports retain forever (the deliverable). **NEVER** add a `user_id` parameter to any new RPC in this pipeline — every RPC resolves the caller via `auth.uid()` (Data invariant 7); only `get_new_user_journey_report_data(p_user_id, ...)` takes a user_id and that's IDOR-pinned (`auth.uid() IS NOT NULL AND <> p_user_id` raises 42501; service role passes through).

### App Store compliance (social apps)
25. **User blocking** — `get_blocked_users()` RPC + `BlockedUsersView` in Settings → Privacy & Security, reachable in ≤3 taps from any profile.
26. **Content reporting** — `report_content(p_table_name, p_record_id, p_reported_user_id, p_content_snippet, p_reason)` with `p_table_name` hard-allowlisted. Long-press "Report & Block" on any user-generated content.
27. **Two-layer moderation** — Layer 1 (client precheck via `moderate-content` with user JWT, blocking) + Layer 2 (DB webhook with service-role `Authorization` + `x-moderation-secret`, async, `is_hidden=true`).
28. **Privacy manifest** — `Fit33/PrivacyInfo.xcprivacy` declares Required Reason APIs + `NSPrivacyCollectedDataTypes`. Verify third-party SPM deps also ship manifests (Xcode → Archive → Distribute → Privacy Report).
29. **Accurate feature copy.** OCR label scanner is OCR, never "barcode lookup". Terms, Privacy Policy, Support docs must all match.
31. **HealthKit purpose strings MUST enumerate the actual categories requested (Apple Review 5.1.1(ii)).** The canonical strings live in `Fit33/Info.plist` lines 65–68 (`NSHealthShareUsageDescription` + `NSHealthUpdateUsageDescription`). Generic copy like "Fit33 tracks your daily steps" is a known App Review rejection vector — every category referenced by `HealthKitManager.requestAuthorization()` (currently: steps, active energy, workouts, body weight, height, biological sex, date of birth on the read side; workouts + active energy on the write side) MUST be listed in the matching purpose string with a plain-language reason. Any PR that adds an `HKObjectType` / `HKCharacteristicType` / `HKQuantityType` to `typesToRead` or `typesToWrite` MUST update the matching Info.plist string in the same PR — the strings are the App Review surface, not internal documentation. Target 25–45 words. Don't ship "Fit33 may write health data" — name what we write.
32. **Sign in with Apple MUST be the FIRST third-party SSO option whenever ANY third-party SSO is offered (HIG 4.8).** Canonical position: top of the auth-button VStack in `Fit33/AuthView.swift`, immediately after `SocialLoginDivider()`, ABOVE Google / Facebook / any future SSO provider. Email + password sign-in stays above the divider in the primary action position; SSO ordering only governs the third-party block. If we ever add a non-Apple SSO without Apple already present, App Review rejects under 4.8 — the codepath that adds a new SSO MUST also add (or already include) `SignInWithAppleButton` in the first slot of that VStack.
33. **Cloud sync of HealthKit-derived data MUST have a user-visible disclosure surface.** Canonical: `HealthDataSyncDetailView` (`Fit33/HealthDataSyncDetailView.swift`) reachable from Settings → Privacy & Security → Health Data. The view is the honest source of truth for which HK categories Fit33 ships off-device — the `syncedCategories` array there MUST stay in lockstep with the `typesToRead` set in `HealthKitManager.requestAuthorization()`. Adding a new HK type that flows into Supabase (via DTO sync, edge function, or any other path) requires adding the matching `(label, icon)` row in `syncedCategories` in the same PR. The "Stop syncing & delete cloud copy" destructive control is REAL as of 2026-07-26 (audit PR-10): it calls the `purge_user_health_data()` RPC (migration #205 — SECURITY DEFINER, `auth.uid()`-scoped, no user parameter) and then `HealthKitService.disconnect()` so purged data doesn't resync; the success banner shows only after the RPC succeeds, and failures surface an honest error alert. **The destructive control MUST NOT lie** — never show the success banner on a failed RPC, and any change to which tables the RPC purges requires updating both the RPC and the `syncedCategories` disclosure list in the same PR.

## Principles
1. **Defense in depth** — RLS + app validation. Never rely on one boundary.
2. **Fail secure** — Auth failures log out, never bypass.
3. **Least privilege** — Anon key + RLS. Admin tokens expire. OAuth scopes minimal.
4. **Log without leaking** — `AppLogger` with PII redaction.
