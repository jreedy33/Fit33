## 1. Critical Bugs (Ship-Blocking)

### BUG-01: CollaborativeLearningEngine is completely non-functional
- **File:** `CollaborativeLearningEngine.swift:300`
- **Issue:** `calculateSimilarity()` accepts `Any` then casts to a named tuple `(goal: String, experience: String, equipment: [String])`. Callers pass a `UserProfile` struct, not a tuple. Swift structs cannot be cast to tuples, so the cast **always fails** and the function **always returns 0**.
- **Why it's a gap:** The entire collaborative recommendation system (similar users, exercise pairings from community data, program success rates) is a complete no-op. No users are ever considered "similar." Every collaborative recommendation returns empty results.
- **Recommendation:** Change the parameter type from `Any` to the actual `UserProfile` struct (or extract the needed fields as a proper struct/protocol). Then access `.goal`, `.experience`, `.equipment` directly.
- **Owner:** Product Engineer Agent
- **Effort:** Small (1 function signature + field access changes)

### BUG-02: Strava data double-counting on every sync
- **File:** `HealthDataService.swift:490`
- **Issue:** `updateDailyActivityFromStrava()` uses `max(current.caloriesBurned, current.caloriesBurned + calories)` which always equals `current + calories` when calories > 0. On every sync cycle, Strava calories/distance/activeMinutes are **re-added** to existing totals instead of being set.
- **Why it's a gap:** Users with Strava connected see wildly inflated daily activity numbers. This cascades into challenge progress (they appear to have burned thousands of extra calories) and league points.
- **Recommendation:** Change to `max(current.caloriesBurned, calories)` — take the higher of the stored value or the incoming Strava value, don't add them.
- **Owner:** Data & Backend Agent
- **Effort:** Small (3 lines — calories, distance, activeMinutes)

### BUG-03: Operator precedence bug in exercise classification
- **File:** `SmartExercisePairingEngine.swift:505`
- **Issue:** `nameLower.contains("calf") || nameLower.contains("raise") && musclesLower.contains(...)` — `&&` binds tighter than `||`, so ANY exercise with "calf" in the name matches regardless of muscle data. "Calf" exercises skip the muscle validation entirely.
- **Why it's a gap:** Exercise substitutions for calf exercises are incorrect — exercises that target completely different muscles could be suggested as calf alternatives.
- **Recommendation:** Add parentheses: `(nameLower.contains("calf") || nameLower.contains("raise")) && musclesLower.contains(...)`
- **Owner:** Product Engineer Agent
- **Effort:** Trivial (add parentheses)

### BUG-04: Duplicate PerformanceMonitor class definitions
- **Files:** `PerformanceOptimizer.swift:212` (`#if DEBUG`) and `PerformanceMonitoringSystem.swift:23` (unconditional)
- **Issue:** Two classes named `PerformanceMonitor` exist. In DEBUG builds both are compiled, causing a duplicate symbol error. In RELEASE, only the one in PerformanceMonitoringSystem survives, but DEBUG-only code expects the other API.
- **Why it's a gap:** Either a compile error or silent API mismatch depending on build config.
- **Recommendation:** Rename the DEBUG version to `DebugPerformanceMonitor` or delete it entirely and unify on the one in PerformanceMonitoringSystem.
- **Owner:** Quality & Performance Agent
- **Effort:** Small

### BUG-05: Duplicate InsightType/InsightCategory enum definitions
- **Files:** `PersonalizedInsightsService.swift` (top-level) and `SmartInsightEngine.swift` (nested in SmartInsight)
- **Issue:** Both define `InsightType` and `InsightCategory` enums with different cases. Depending on scope resolution, code may reference the wrong enum.
- **Why it's a gap:** Type confusion — insights generated by one engine may not be displayable by views expecting the other engine's types.
- **Recommendation:** Consolidate into a single shared `InsightType` enum (see consolidation item DUP-08).
- **Owner:** Product Engineer Agent
- **Effort:** Medium

### BUG-06: Challenge progress logged to "pending" (unaccepted) challenges
- **File:** `ChallengeService.swift:2131`
- **Issue:** `logProgressFromSource()` processes challenges with `status == "pending"`. The creator accumulates progress before the opponent accepts, giving an unfair head start.
- **Why it's a gap:** Competitive integrity — a user could have days of progress before their opponent even sees the challenge.
- **Recommendation:** Change guard to `challenge.status == "active"` only. The group challenge loop at line 2147 already correctly checks `challenge.isActive && challenge.iHaveAccepted`.
- **Owner:** Product Engineer Agent
- **Effort:** Trivial (remove `|| challenge.status == "pending"`)

### BUG-07: Leaderboard shows lower progress than challenge cards
- **File:** `ChallengeService.swift:2595-2692`
- **Issue:** `ChallengeProgressResolver.liveProgress()` for `CommunityLeaderboardResponse` and `CommunityDetailResponse` uses `value > 0 ? value : serverValue` instead of `max(localValue, serverValue)` used by all other overloads.
- **Why it's a gap:** A user could see 8000 steps on their challenge card but only 5000 steps on the leaderboard for the same challenge. This erodes trust in the data.
- **Recommendation:** Standardize all 6 overloads to use `max(localValue, serverValue)`.
- **Owner:** Product Engineer Agent
- **Effort:** Small (2 functions)

### BUG-08: DailyResetService.fetchStepCountForDate always returns nil
- **File:** `DailyResetService.swift:467-471`
- **Issue:** The function is a stub that always returns `nil`. Daily summaries always record 0 steps.
- **Why it's a gap:** The daily archive feature is missing step data entirely. Historical daily summaries are incomplete, affecting insights and trend analysis.
- **Recommendation:** Implement using `HealthKitManager.shared` or `HealthKitService.shared` to query steps for the given date.
- **Owner:** Product Engineer Agent
- **Effort:** Small

### BUG-09: ForceExerciseRefresh strips metadata from exercises
- **File:** `ForceExerciseRefresh.swift`
- **Issue:** The sync logic is far less thorough than `ExerciseLibraryService.performSync()`. It omits `movementPattern`, `forceType`, all ratings fields, and family data (`exerciseFamily`, `complementaryFamilies`).
- **Why it's a gap:** Users who tap "Force Refresh" in settings lose exercise metadata, breaking limitation filtering (which depends on metadata), exercise swaps (which depend on family data), and workout quality scoring.
- **Recommendation:** Replace the inline sync logic with a call to `ExerciseLibraryService.shared.performSync(force: true)`.
- **Owner:** Product Engineer Agent
- **Effort:** Small (replace function body with delegation)

### BUG-10: ExercisePerformanceService column name mismatch
- **File:** `ExercisePerformanceService.swift`
- **Issue:** DTO uses `best_set_weight` / `best_set_reps` but `ExerciseHistoryService` saves as `max_weight` / `max_reps`. If these reference the same Supabase table, one service can't read the other's data.
- **Why it's a gap:** Progressive overload suggestions may return empty/incorrect data because the column names don't match what was written.
- **Recommendation:** Verify the actual Supabase table schema and align both services to the correct column names.
- **Owner:** Data & Backend Agent
- **Effort:** Small

### BUG-11: StoreKit willAutoRenew hardcoded to true
- **File:** `StoreKitManager.swift:162`
- **Issue:** `willAutoRenew` is always `true` regardless of actual subscription renewal status.
- **Why it's a gap:** Users who cancelled their subscription still see "will auto-renew" in the UI, causing confusion and potential support tickets.
- **Recommendation:** Read the actual `renewalInfo` from StoreKit 2's `Product.SubscriptionInfo.RenewalInfo`.
- **Owner:** Infra & Security Agent
- **Effort:** Small

### BUG-12: ContextualMealEngine hardcoded nutritional targets
- **File:** `ContextualMealEngine.swift`
- **Issue:** Uses fixed values (2200 cal, 160g protein, 250g carbs, 70g fat) for every user instead of pulling from user profile/goals.
- **Why it's a gap:** A 110 lb female cutting weight gets the same macro targets as a 220 lb male bulking. Meal suggestions are wrong for most users.
- **Recommendation:** Pull targets from user profile (TDEE calculation in BodyCompositionTrackingService or InBodyService) and goal-specific macro splits.
- **Owner:** Product Engineer Agent
- **Effort:** Medium

## 2. High-Priority Logic Gaps

### GAP-01: StreakShieldService not integrated with DailyResetService
- **File:** `DailyResetService.swift` → `UserManager.checkAndBreakStreakIfNeeded()`
- **Issue:** `DailyResetService` calls `UserManager.shared.checkAndBreakStreakIfNeeded()` but there's no verification that `StreakShieldService` is consulted before breaking a streak.
- **Why it's a gap:** A premium user who earned a streak shield could still have their streak broken if UserManager doesn't independently check shields.
- **Recommendation:** In `UserManager.checkAndBreakStreakIfNeeded()`, check `StreakShieldService.shared.useShieldIfAvailable()` before resetting the streak.
- **Owner:** Product Engineer Agent

### GAP-02: ContactsService downloads ALL user profiles
- **File:** `ContactsService.swift:335`
- **Issue:** `findMatchingUsersDirect()` fetches every `user_profiles` row (id, name, email, username, profile_photo_url, phone_number) to do client-side phone matching.
- **Why it's a gap:** Security risk (leaking all users' phone numbers to every client) and performance issue (unbounded result set). At scale, this will crash or time out.
- **Recommendation:** Move phone matching to a Supabase RPC function that accepts hashed phone numbers and returns only matching profiles. Never send all phone numbers to the client.
- **Owner:** Data & Backend Agent + Infra & Security Agent

### GAP-03: DailyQuestService passes total steps as increment
- **File:** `DailyQuestService.swift:636-648`
- **Issue:** `onStepsUpdated()` passes `todaySteps` as the `increment` parameter to `reportProgress()`. If the server RPC adds this to the existing value, steps are double-counted on every update.
- **Why it's a gap:** Quest progress could show 20,000 steps when the user only walked 5,000.
- **Recommendation:** Either pass the delta (today's steps minus last reported value) or change the RPC to upsert/set instead of increment.
- **Owner:** Product Engineer Agent + Data & Backend Agent

### GAP-04: Calorie challenge type ambiguity
- **File:** `ChallengeService.swift:2349-2352`
- **Issue:** `.calories` case uses `max(hkCalories, mealCalories)` — mixing burned calories (HealthKit) with consumed calories (meals). These are fundamentally different metrics.
- **Why it's a gap:** A "burn 500 calories" challenge could be completed by eating 500 calories, and vice versa.
- **Recommendation:** Split into `.caloriesBurned` and `.caloriesConsumed` challenge types, or document which metric `.calories` represents and only use that source.
- **Owner:** Product Engineer Agent

### GAP-05: Walk/Run distance truncation
- **File:** `ChallengeService.swift` (all liveProgress overloads)
- **Issue:** Uses `Int(km)` which truncates rather than rounds. 4.9 km shows as 4 km; 1.99 miles shows as 1 mile.
- **Why it's a gap:** Users feel cheated when they're 90% to the next unit but it doesn't count. This is especially frustrating for 1-mile or 1-km challenges.
- **Recommendation:** Use `Int(km.rounded())` or switch to tracking in meters/feet to avoid rounding entirely.
- **Owner:** Product Engineer Agent

### GAP-06: ProgressiveExerciseUnlockService non-deterministic gating
- **File:** `ProgressiveExerciseUnlockService.swift`
- **Issue:** `shouldIncludeExercise()` uses `Double.random(in: 0...1) < profile.varietyPercentage` for non-foundational exercises. Calling it twice for the same exercise can return different results.
- **Why it's a gap:** Exercise lists randomly change on every render, causing UI flicker. A user browsing exercises sees a different list each time they scroll.
- **Recommendation:** Seed the random decision with a deterministic hash of `(exerciseName + date)` so the result is stable within a day but varies across days.
- **Owner:** Product Engineer Agent

### GAP-07: ExercisePopularityService.getTopExercises ignores category parameter
- **File:** `ExercisePopularityService.swift`
- **Issue:** The `category` parameter is accepted but never used in the filtering logic. All categories return the same top exercises.
- **Why it's a gap:** UI sections like "Popular Chest Exercises" show the globally popular exercises (bench press, squats, etc.) regardless of the requested category.
- **Recommendation:** Filter the popularity scores by the passed category before sorting.
- **Owner:** Product Engineer Agent

### GAP-08: BodyCompositionTrackingService uses male-only body fat thresholds
- **File:** `BodyCompositionTrackingService.swift:313-334`
- **Issue:** Body fat insights use male thresholds (8% very low, 15% athletic, 25% high) for all users. Female users with 22% body fat (healthy/athletic for women) would be told they're "approaching high body fat."
- **Why it's a gap:** Incorrect health guidance for roughly half the user base.
- **Recommendation:** Add gender-aware thresholds. Female ranges: essential ~12%, athletic ~18%, fitness ~25%, high ~32%.
- **Owner:** Product Engineer Agent

### GAP-09: Brand name inconsistency in HealthKit workouts
- **File:** `HealthKitManager.swift:141,196`
- **Issue:** Line 141 saves workouts with source name "GoFit", line 196 uses "Fit33".
- **Why it's a gap:** Workouts appear under different app names in Apple Health, confusing users and breaking workout source filtering.
- **Recommendation:** Standardize to "Fit33" everywhere. Also update `StoreKitManager.swift:12-13` which uses "com.gofit.app" product IDs.
- **Owner:** Product Engineer Agent

### GAP-10: WeightTrackingService goalProgress wrong for weight gain goals
- **File:** `WeightTrackingService.swift:289`
- **Issue:** `goalProgress` calculation assumes weight loss (start - current / start - target). For gain goals where target > start, the denominator is negative, producing nonsensical negative progress.
- **Why it's a gap:** Users with bulking/gaining goals see broken progress indicators.
- **Recommendation:** Use `abs(current - start) / abs(target - start)` and clamp to 0...1.
- **Owner:** Product Engineer Agent

### GAP-11: WorkoutGeneratorService drops equipmentIsMostlyMachines parameter
- **File:** `WorkoutGeneratorService.swift`
- **Issue:** `exerciseCountForDuration()` delegates to `WorkoutComboRules.getExerciseCountForDuration()` but silently drops the `equipmentIsMostlyMachines` parameter.
- **Why it's a gap:** Machine-heavy workouts don't get the adjusted (higher) exercise count that accounts for shorter machine setup times. Users in machine-only gyms get too few exercises.
- **Recommendation:** Pass the parameter through to `WorkoutComboRules`.
- **Owner:** Product Engineer Agent

### GAP-12: Two conflicting WorkoutLocation enums
- **Files:** `ExerciseFilterService.swift` (capitalized: "Gym", "Home") vs `EquipmentHierarchyService.swift` (lowercase: "gym", "home")
- **Issue:** Either a compile error (if both in scope) or silent data mismatch (string comparisons fail).
- **Why it's a gap:** Location-based exercise filtering may silently fail, showing gym exercises for home workouts or vice versa.
- **Recommendation:** Consolidate into one `WorkoutLocation` enum in a shared location. Use it everywhere.
- **Owner:** Product Engineer Agent

### GAP-13: ExerciseNicknameService.autoCapitalize returns wrong value
- **File:** `ExerciseNicknameService.swift`
- **Issue:** Processes text into a result variable but returns based on `text.dropFirst()` (the original input) instead of the processed result.
- **Why it's a gap:** Custom exercise nicknames are not properly capitalized.
- **Recommendation:** Return the processed result variable instead of `text.dropFirst()`.
- **Owner:** Product Engineer Agent

### GAP-14: LimitationFilterIntegration calls engine with empty data
- **File:** `LimitationFilterIntegration.swift`
- **Issue:** `evaluateAgainstLimitation()` calls `LimitationFilterEngine.applyLimitations()` with an empty exercises array, ignores the (empty) result, then re-implements all evaluation logic locally.
- **Why it's a gap:** The engine call is dead code, and the local re-implementation may drift from the engine's logic over time.
- **Recommendation:** Either properly delegate to the engine or delete the dead call.
- **Owner:** Product Engineer Agent

## 3. Duplicate Logic — Consolidation Plan

### DUP-01: resolvedType computed property (16 copies across 3 files)
- **Files:** `ChallengeService.swift` (5 structs), `CommunityChallengeService.swift` (6 structs), `PrivateChallengeService.swift` (3 structs), plus Views
- **Issue:** Identical `resolvedType: ChallengeType` computed property copy-pasted across 16 model structs.
- **Why it's a gap:** Any bug fix or new challenge type must be applied to 16 locations. This has already caused inconsistencies (the leaderboard version differs subtly).
- **Recommendation:** Extract into a protocol extension:
  ```swift
  protocol ChallengeTypeResolvable {
      var challengeType: String { get }
      var targetUnit: String { get }
      var title: String { get }
  }
  extension ChallengeTypeResolvable {
      var resolvedType: ChallengeType { /* single implementation */ }
  }
  ```
  Then conform all 16 structs to this protocol.
- **Owner:** Product Engineer Agent
- **Effort:** Medium (protocol + 16 conformances, but each conformance is just adding the protocol name)

### DUP-02: liveProgress copied 6 times with subtle inconsistencies
- **File:** `ChallengeService.swift:2324-2692`
- **Issue:** 6 overloads of `ChallengeProgressResolver.liveProgress(for:)` with nearly identical switch-case bodies but subtle differences (max vs conditional, see BUG-07).
- **Recommendation:** Extract the progress calculation into a single function that accepts `(challengeType: ChallengeType, targetUnit: String, serverValue: Int)` and returns the resolved progress. Each overload becomes a 2-line wrapper.
- **Owner:** Product Engineer Agent
- **Effort:** Medium

### DUP-03: syncAllTrackingTo* copied 3 times
- **Files:** `ChallengeService.swift:1820`, `CommunityChallengeService.swift:1232`, `PrivateChallengeService.swift:1273`
- **Issue:** Three nearly identical sync functions reading from the same HealthKit/Hydration/Meal sources. Any new challenge metric must be added to all three.
- **Recommendation:** Extract a shared `ChallengeProgressSource` that reads all tracking data once, then each service calls its own `logProgress` RPC with the shared data.
- **Owner:** Product Engineer Agent
- **Effort:** Medium

### DUP-04: MovementPattern enum (4 different versions)
- **Files:** `IntelligentWorkoutGenerator.swift` (10 cases), `WorkoutGeneratorService.swift` (~15 cases), `SmartExerciseSelectionEngine.swift` (~20 cases), `SmartExercisePairingEngine.swift` (30 cases)
- **Issue:** Four separate `MovementPattern` enums with different case sets. Movement classification logic is duplicated across 6+ files.
- **Recommendation:** Create a single `MovementPattern` enum in a shared file (e.g., `ExerciseTypes.swift`) with the full 30-case set from SmartExercisePairingEngine. Add a `simplified` computed property for code that only needs broad categories. Consolidate all classification logic into one `classifyMovementPattern()` function.
- **Owner:** Product Engineer Agent
- **Effort:** Large (touches many files, but each change is mechanical)

### DUP-05: Equipment normalization (6+ implementations)
- **Files:** `ExerciseFilterService.normalizeEquipment()` (canonical), `EquipmentHierarchyService`, `ExerciseIntelligenceEngine`, `ExerciseMappingService`, `ProgressiveExerciseUnlockService`, `SmartExerciseSelectionEngine`, `SmartExercisePairingEngine`, `WorkoutGeneratorService`
- **Issue:** 6+ independent implementations of equipment name normalization.
- **Also:** `ExerciseFilterService.normalizeEquipment()` normalizes to `"Bands"` but `allEquipment` lists `"Resistance Bands"` — internal inconsistency.
- **Recommendation:** Make `ExerciseFilterService.normalizeEquipment()` the single source of truth. Fix the Bands/Resistance Bands mismatch. All other files should call this function instead of maintaining their own mappings.
- **Owner:** Product Engineer Agent
- **Effort:** Medium

### DUP-06: Exercise substitution (2 competing engines)
- **Files:** `AlternativeExerciseEngine.swift` and `SmartExercisePairingEngine.swift`
- **Issue:** Two separate engines for finding exercise alternatives with different algorithms, different scoring, and different muscle group mappings.
- **Recommendation:** Audit which engine each UI calls. Consolidate into `SmartExercisePairingEngine` (it's more sophisticated with 30 movement patterns). Redirect AlternativeExerciseEngine callers to SmartExercisePairingEngine. Delete AlternativeExerciseEngine.
- **Owner:** Product Engineer Agent
- **Effort:** Medium

### DUP-07: Triple-fetch of all exercises from Supabase
- **Files:** `ExerciseLibraryService.performSync()`, `ExerciseIntelligenceEngine.loadFromDatabase()`, `ExerciseMappingService.buildMaps()`
- **Issue:** Three independent full-table fetches of the same exercises data from Supabase. Wastes bandwidth and battery.
- **Recommendation:** Fetch once via `ExerciseLibraryService` and share the result. ExerciseIntelligenceEngine and ExerciseMappingService should accept an `[ExerciseDTO]` parameter rather than fetching independently.
- **Owner:** Product Engineer Agent + Data & Backend Agent
- **Effort:** Medium

### DUP-08: Three separate insight engines
- **Files:** `PersonalizedInsightsService.swift`, `SmartInsightEngine.swift`, `AdvancedIntelligenceService.swift`
- **Issue:** All three analyze nutrition-performance correlations independently. PersonalizedInsightsService and AdvancedIntelligenceService both track protein-to-workout-quality correlations and both write to Supabase. SmartInsightEngine duplicates streak/milestone logic.
- **Recommendation:** Merge SmartInsightEngine into PersonalizedInsightsService (rule-based insights are a subset of the personalized system). Clarify AdvancedIntelligenceService as the "write to Supabase for analytics" layer and PersonalizedInsightsService as the "read and display to user" layer. Eliminate duplicate correlation tracking.

### DUP-09: Three separate program goal/duration enums

### DUP-10: Google OAuth URL construction (exact duplicate)

- **Effort:** Trivial

### DUP-11: HealthKit step tracking (overlapping responsibility)

### DUP-12: Body composition insights (2 implementations)

- **Issue:** Both provide body fat analysis and recommendations with different thresholds.

### DUP-14: Memory/CPU measurement (5 copies)

## 5. Security Concerns

### SEC-01: OAuth tokens in plain UserDefaults
- **Files:** `FitbitService`, `StravaService`, `InBodyService`
- **Issue:** Access tokens and refresh tokens stored in `UserDefaults` instead of Keychain. Accessible to any code with UserDefaults access; not encrypted at rest on non-passcode devices; included in device backups.
- **Recommendation:** Migrate all OAuth tokens to Keychain using `SecItemAdd`/`SecItemCopyMatching`. Add a migration path that reads from UserDefaults once, saves to Keychain, then deletes the UserDefaults entry.
- **Owner:** Infra & Security Agent
- **Effort:** Medium

### SEC-02: ContactsService exposes all user phone numbers
- **File:** `ContactsService.swift:335`
- **Issue:** Downloads every user's phone number and email for client-side matching.
- **Recommendation:** See GAP-02. Server-side phone hash matching.
- **Owner:** Data & Backend Agent + Infra & Security Agent
- **Effort:** Large

### SEC-03: Phone verification rate limiting bypassable
- **File:** `PhoneVerificationService.swift`
- **Issue:** `remainingAttempts` counter is in-memory only. Force-quit resets it.
- **Recommendation:** Persist the counter and timestamp in UserDefaults (or better, enforce rate limiting server-side in the edge function).
- **Owner:** Infra & Security Agent
- **Effort:** Small

### SEC-04: Push notification single device token
- **File:** `PushNotificationService.swift`
- **Issue:** Upserts on `user_id` conflict, so a user can only have ONE device token. Multi-device users lose notifications on all but the most recently used device.
- **Recommendation:** Change upsert key to `(user_id, device_token)` or maintain a device tokens array.
- **Owner:** Data & Backend Agent
- **Effort:** Small

## 6. Performance Issues

### PERF-01: DateFormatter as computed property
- **Files:** `HydrationService.swift`, `WeightTrackingService.swift`
- **Issue:** `dateFormatter` is a computed property creating a new instance on every access. DateFormatter is expensive to construct.
- **Fix:** Change to `static let` or `lazy var`.
- **Owner:** Quality & Performance Agent

### PERF-02: ISO8601DateFormatter created 7+ times per sync
- **File:** `HealthDataService.swift`
- **Fix:** Create one shared instance.
- **Owner:** Quality & Performance Agent

### PERF-03: ExerciseNameCache arbitrary eviction
- **File:** `ExerciseNameCache.swift`
- **Issue:** `saveToDisk()` evicts entries using `Array(memoryCache.keys.prefix(...))`. Dictionary key ordering is random, so frequently-needed entries may be evicted while stale ones persist.
- **Fix:** Track access timestamps and evict LRU, or simply cap the cache at a reasonable size without eviction (exercise names are small).
- **Owner:** Quality & Performance Agent

### PERF-04: FavoriteBasedDiscoveryEngine in-memory-only state
- **File:** `FavoriteBasedDiscoveryEngine.swift`
- **Issue:** Cooldown tracking, variant rotation, and discovery state reset on every app restart. The 3-day cooldown is only effective within a single session.
- **Fix:** Persist cooldown dictionaries to UserDefaults.
- **Owner:** Product Engineer Agent

### PERF-05: SmartExercisePairingEngine thread safety
- **File:** `SmartExercisePairingEngine.swift`
- **Issue:** `initialize()` sets `isInitialized = true` from a background thread with no synchronization. `findSubstitutes()` may access Core Data off the main thread.
- **Fix:** Use `@MainActor` isolation or a proper synchronization mechanism.
- **Owner:** Quality & Performance Agent

### PERF-06: UserBehaviorLearningEngine data race
- **File:** `UserBehaviorLearningEngine.swift:24`
- **Issue:** `LearningCacheStorage` is `@unchecked Sendable` with mutable dictionaries and no synchronization. `@MainActor` engine writes to it while `nonisolated` scoring reads from it.
- **Fix:** Use an actor or `OSAllocatedUnfairLock` to synchronize cache access.
- **Owner:** Quality & Performance Agent

### PERF-07: RequestDeduplicationService unnecessary NSLock
- **File:** `PerformanceOptimizations.swift:37`
- **Issue:** Class is `@MainActor` but uses `NSLock`. The lock is unnecessary overhead since everything runs on the main thread.
- **Fix:** Remove the `NSLock`. If cross-thread access is ever needed, convert to an actor.
- **Owner:** Quality & Performance Agent
